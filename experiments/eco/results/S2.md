Micro-trials, run in batches of at most $20 with `tools/Start-Batch.ps1` (random order, budget
stop). The owner sends the `/usage` reading with every message; readings are logged locally.

Also found:

  every opus review's cost; sonnet reviewers never ran it. A candidate saving to test in S3.

  missed and every opus reviewer of RV2 found: a check log is read "only on a failure", so a
  cheap runner's PASS reaches the merge gate unread. Fix it before eco v2 is proposed (S5).

Spend: $42.84 API-equivalent on runs (runner $0.78, exploration $1.14, review $37.48 including
one invalid run cut by the session limit, implementation $3.44), plus operator overhead.
Weekly `/usage` went from 3% (end of S1) to 23% before the last $8.80 review batch. Calibration
over S2: one weekly percent is about $2.2 and a five-hour window holds about $18 (one session
percent about $0.18); S1's $0.26 per session percent was too high.

## Runner (H3)

Base `1a8526e`, primary opus medium, `D-agents.json`; checks restore, C2, C6, C4, C5. Two runs
per variant, $0.78 in total.

| Variant | Cost | Primary calls | Subagent | Wall |
| --- | --- | --- | --- | --- |
| self | $0.22, $0.22 | 4, 4 | none | 0.8, 0.6 min |
| delegated (haiku `runner`) | $0.17, $0.17 | 2, 2 | 7 and 6 calls, cold start 7.7k, $0.004 | 0.7, 0.7 min |

all passing; a failing check, whose output the primary must read anyway, may change this.

## Exploration (H6, H9)

Base `1a8526e`, haiku low primary that only delegates, six questions X1-X6, two repeats per
variant, 72 runs, $1.14 in total (whole runs). Accuracy scored against the key (2 correct and
complete, 1 partial, 0 wrong) by a sonnet subagent, spot-checked by the operator on X1. Costs
are the scout subagent's own.

| Variant | Accuracy (mean of 2) | X1 | Scout cost | Calls | Cold start | Tool use |
| --- | --- | --- | --- | --- | --- | --- |
| scout-grep (haiku) | 1.75 | 0.5 | $0.0036 | 5.2 | 3,979 | Grep, Read |
| scout-lsp (haiku) | 1.75 | 0.5 | $0.0037 | 5.3 | 4,846 | LSP never called |
| scout-claudemd (haiku, CLAUDE.md) | 1.75 | 0.5 | $0.0043 | 4.9 | 7,987 | LSP never called |
| scout-graphify (haiku) | 1.67 | 0 | $0.0044 | 5.2 | 5,561 | `graphify` in 17 calls |
| Explore (built-in, haiku) | 1.75 | 0.5 | $0.0047 | 3.8 | 18,642 | Grep, Read |
| scout-sonnet (sonnet medium) | 2.00 | 2 | $0.0319 | 3.7 | 4,835 | LSP never called |

- X2-X6 (locate a member or a value): every variant scored 2 in both repeats. Only X1, which
  needs a cause (the fill keeps the default stretch alignment in a star column, so the width
  animation grows it around the centre), separates them: both sonnet runs found it, no haiku
  run did; haiku answers named the right files or a wrong mechanism.
- H6 (lean roles): supported at equal accuracy. The lean scout is about 23% cheaper than the
  built-in Explore (cold start 4k against 18.6k tokens); loading CLAUDE.md costs 4k tokens of
  cold start and 17% more for no accuracy gain.
- H9 (code intelligence): not supported. With the LSP tool present and the prompt saying to
  prefer it, haiku and sonnet scouts never called it in 36 runs; the tool only adds 870 tokens
  of cold start. graphify was used but gave no accuracy gain (worst on X1) at 22% more cost.
- Absolute scout costs are under one cent; what matters in real work is that a scout keeps the
  search out of the primary's context. Rule of thumb from this trial: a haiku lean scout for
  "where is" questions, a sonnet scout for "why" questions.
- Key notes from scoring: X4's effective default is `LedgerPreferences.RefreshMinutes = 5`
  (`LedgerContract.cs`); `DefaultRefreshInterval` seeds the initial state. X6's Codex client only
  carries Retry-After into `CodexException`. Neither changed a score.

## Review (H5), first repeat

Four changes (RV1-RV3 with defect keys, RV4 a clean control), haiku low primary that only
delegates, `D-agents.json`; variants: lean `reviewer` at sonnet high, opus medium and opus high,
and the repository `aiu-reviewer` (opus high). One run per cell, 16 valid runs, $27.14 (plus one
run cut by the session limit, $1.54, excluded). Scored blind against the key by a sonnet
subagent; the operator spot-checked RV2 opus high item by item and agreed.

| Variant | Key recall (of 15) | Important found (of 6) | False alarms | Cost (4 runs) | `/code-review` share |
| --- | --- | --- | --- | --- | --- |
| reviewer, sonnet high | 8 | 3.5 | 0 | $2.22 | never called |
| reviewer, opus medium | 9.5 | **6** | 0 | $7.56 | 27% |
| reviewer, opus high | 5.5 | 4 | 0 | $8.38 | 23% |
| aiu-reviewer, opus high | 8.5 | 5 | 0 | $8.98 | 21% |

- Important items: D1, D2, E1, E2, E3 from the key, plus one unkeyed finding the scorer
  confirmed valid: the eco skill reads a check log "only on a failure", so a cheap runner's PASS
  reaches the merge gate unread (conflicts with CONTRIBUTING and verification.md; the real
  fixes left it). Every opus run on RV2 found it; sonnet approved RV2.
- RV4 control: all 16 runs approved with Minor notes only, so no false alarms anywhere.
- Never found by any variant: D4, D5, E6, S3 (all Minor). S3 (the `SettingsButton` id is not
  unique) is real; one review called the lookup "already proven".
- Cost: opus medium is not cheaper than opus high on these diffs (RV2 equal, RV3 13% less);
  effort mostly changes thinking, while reads and the diff dominate. Opus reviewers always ran
  the contract's local `/code-review`, which forks a same-model agent: $0.08-1.17 per run. Sonnet
  reviewers never ran it.
- Reading (one run per cell, so not yet proven): H5 is supported on its first half: sonnet
  missed Important items on RV1 and RV2 at 30% of the cost. Opus high added no recall over opus
  medium, including on the T3 change RV2 (4 against 6 Important). Only opus medium found every
  Important item, the plan's adoption rule.
- Second repeat, targeted instead of all 16 cells: sonnet and opus medium on RV1-RV3, and opus
  high on RV2 (7 runs, about $10).

## Review (H5), second repeat and combined

Seven runs, $8.80, all valid, scored blind by a sonnet subagent with the same standard; the
unkeyed RV2 item ("X", the unread PASS log) was added to the key as Important.

| Variant (RV1-RV3) | Important found, rep 1 + rep 2 (of 12) | Key recall incl. Minor, 2 reps (of 30) | False alarms | Cost, 2 reps |
| --- | --- | --- | --- | --- |
| reviewer, sonnet high | 3.5 + 4 = **7.5** | 15 | 1 (rep 2, RV2) | $4.03 |
| reviewer, opus medium | 6 + 5 = **11** | 16.5 | 0 | $12.15 |
| reviewer, opus high (RV2 only, of 4 per rep) | 2 + 2 = 4 of 8 | - | 0 | $2.93 |

- The result reproduces. Opus medium missed one Important item in six reviews (E1 once); sonnet
  half-found D2 once and missed it once, and missed E2 and X in one RV2 run and E3 in the
  other. On Minor items the two are close, so the gap is in what matters most.
- Opus high on the T3 change found 2 of 4 Important items in both repeats, against 4 and 3 for
  opus medium at lower cost: H5's "opus high adds recall on T3" is not supported here.
- Every variant missed S3 (the non-unique `SettingsButton` id) in every run, and D4 and D5 in
  every run: some defects need a check the reviewer does not think of, whatever the model.
- Decision for arm E: reviewer at opus medium. Sonnet is a third of the cost but fails the
  plan's adoption rule (every known Important defect).

## Implementation (H4)

Haiku low primary that only delegates to the lean `implementer` (`D-agents.json`, cold start
about 21k), two repeats per cell, 10 runs, $3.44 in total. IM1 scored with the held-out
`PeakHoursTests` from `8eaf1f7` minus its view-model test (`C:\aiu-exp\score-im1.ps1`); IM2 by
comparing the diff with `42719a1` and rebuilding the UI test project in Release by the operator.

| Brief | Implementer | Run cost | Score |
| --- | --- | --- | --- |
| IM1 (needs judgment) | sonnet high | $0.33, $0.29 | 9/9, 9/9 |
| IM1 | opus medium | $0.46, $0.54 | 9/9, 9/9 |
| IM2 (fully specified) | sonnet high | $0.22, $0.29 | 3/3 fixes, build PASS; 3/3, PASS |
| IM2 | opus medium | $0.63, $0.58 | 3/3, PASS; 3/3, PASS |
| IM2 | haiku xhigh | $0.05, $0.05 | 3/3, PASS; 3/3, PASS |

- Every run committed, reported its checks correctly (no false PASS) and made no unrelated edits.
  The haiku primary reported DONE_WITH_CONCERNS in 8 of 10 runs, for the clone's limits (no
  `origin/main`, smokes NOT_RUN) or for not re-running the implementer's checks; the work was sound.
- IM2 runs differ only in how the tooltip check matches the text (the tooltip's name, a child
  element, or both, as `42719a1` does). The variation crosses models in both directions, so it
  is noise, not a model effect; only a desktop smoke could tell the forms apart.
- H4 is supported, and more strongly than stated: sonnet high matched opus medium on both the
  judgment brief and the specified brief at 40-55% of the cost, and haiku xhigh matched both on
  the specified brief at under a tenth. Caveat: both briefs are small and precise (one file and
  its tests; three named fixes); a brief with open design questions was not tested here.
