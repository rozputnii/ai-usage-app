## Findings

### B5-F1 — The AIU record system is already a "right-sized" SDD; no external framework fits better
- **Observation:** The repo already prescribes what SDD frameworks sell: per-feature spec
  with testable AC-xx, optional design and tasks, an evidence-only verification record,
  a canonical backlog, a validator with `--final`, and an explicit rule that small fixes need
  no spec (CONTRIBUTING "Records"). Small features already run light: AIU-050/051/052 have
  only spec.md + verification.md (~500 words each).
- **Evidence:** CONTRIBUTING.md "Records"; docs/workflow/formats.md; AIU-050..052 folders.
  Spec Kit = specify → plan → tasks → implement, branch per spec, Python CLI plus
  agent scaffolding, 157 community extensions "not audited or endorsed" (history page).
  Böckeler: Spec Kit produced "many repetitive markdown files" and felt like overkill for a
  3-5 point feature; Kiro turned a small bug into 4 user stories and 16 ACs.
- **Label:** FACT (repo, sources); INFERENCE (fit).
- **Confidence:** High.
- **Impact:** Quality neutral; speed negative if a framework is adopted (duplicate templates,
  a second source of truth, branch-per-spec contradicts main-only Git policy).
- **Proposed direction:** Keep the AIU system as the only spec system. Borrow two narrow ideas
  (F2) instead of a tool.
- **Verdict:** Reject Spec Kit, BMAD, Tessl, OpenSpec as tools; adapt ideas.
- **Security/supply-chain:** Each installs code into the repo/agent (pip/uv CLI, npx
  installer, community extensions); avoided by rejection.
- **Effort and upkeep:** Zero.
- **KEEP:** spec.md with AC-xx, verification.md as evidence only, backlog as status owner,
  validator `--final`, "small fixes need no spec".

### B5-F2 — Ceremony is chosen by owner habit, not by an explicit risk tier; borrow "size after investigating"
- **Observation:** CONTRIBUTING distinguishes "small fixes" from "features" but gives no
  criteria, so the agent picks the record set. AIU-055 (11 tasks, ~2,300 changed lines in
  src/tests) produced spec 2,168 words + tasks 6,103 words + verification 2,711 words
  (~11k words). The tasks file restates spec values as "Global Constraints" and embeds an
  entire orchestration manual (execution model, worker brief, 9-step worker procedure).
- **Evidence:** `wc -w docs/specs/AIU-055*/*`; `git diff --stat 22e1324 87c34e6 -- src tests`
  (43 files, +2301/-281). BMAD v6.12.0: "Build decides how much ceremony a change needs after
  investigating it, not before"; simple changes get a two-section spec. Kiro: "Quick Spec"
  without approval gates and a "bugfix spec" of current / expected / unchanged behavior.
  Claude Code best practices: "If you could describe the diff in one sentence, skip the plan."
- **Label:** FACT (counts, sources); INFERENCE (cause).
- **Confidence:** High.
- **Impact:** Speed: medium gain (less authoring and owner reading). Quality: neutral if ACs
  and evidence are kept.
- **Proposed direction:** Add a 4-row tier table to CONTRIBUTING "Records", decided by the
  agent after a short investigation and stated in its first plan line:
  T0 fix (commit-message plan + evidence), T1 small feature (spec ≤ ~1 page with ACs +
  verification), T2 multi-part feature (adds tasks.md only when work is parallel),
  T3 security/data-lifecycle (adds design + mandatory focused review). For bugs, allow a
  three-heading spec: current, expected, unchanged behavior (Kiro idea; the "unchanged"
  heading is a cheap regression guard). Move the reusable worker procedure out of each
  tasks.md into one skill or agent definition (F9) so tasks.md holds only task blocks.
- **Verdict:** Adapt idea.
- **Security/supply-chain:** None.
- **Effort and upkeep:** Small doc edit; lowers upkeep.
- **KEEP:** UI-variants-first rule (owner direction 2026-10-07); AC identifiers; the owner's
  right to ask for a heavier tier.

### B5-F3 — Records duplicate evidence and status across tasks.md, verification.md and commits
- **Observation:** In AIU-055 the controller made a `docs(AIU-055): record T-0n` commit after
  each worker, copying worker report rows into verification.md and status/evidence into
  tasks.md. Of 33 AIU-055 commits, these record commits are a large share; verification.md
  holds ~20 per-task rows plus the integrated T-12 table that supersedes them. Spec
  `approval_basis` is a long narrative paragraph of the owner conversation.
- **Evidence:** `git log --grep AIU-055` (33 commits, 17:41–19:54 on 2026-10-08);
  AIU-055 verification.md "Per-task evidence"; formats.md ("verification.md: actual evidence,
  not another status mirror").
- **Label:** FACT; INFERENCE (cost).
- **Confidence:** Medium-high.
- **Impact:** Speed: small-medium gain; quality neutral (the integrated run is the evidence
  that matters for the merged state).
- **Proposed direction:** For parallel runs, verification.md records the integrated checks,
  review verdict, known limits and NOT_RUN table; per-task evidence lives in the worker's
  commit message (it already carries test counts) and the git-ignored report. Cap
  `approval_basis` at decision IDs plus one sentence; the D-xxx record holds the detail.
- **Verdict:** Adapt idea.
- **Security/supply-chain:** None.
- **Effort and upkeep:** Small; reduces commits and merge conflicts on shared docs.
- **KEEP:** PASS/FAIL/NOT_RUN/BLOCKED per AC with command and commit ref; honest NOT_RUN.

### B5-F4 — Parallel autonomous workers paid off once, but should be the exception, not the default
- **Observation:** AIU-055 ran 11 autonomous worktree workers that each restored, baselined,
  implemented test-first, ran smokes under a shared desktop lock, got an opus review, merged
  and pushed to main. It finished in ~2h13m with all ACs met — a real success. Costs were
  visible: every worker repeated restore/baseline/smoke; the interactive desktop is a
  serialized shared resource; smokes interfered with the owner's installed app (T-09/T-10);
  the controller spent its turns recording. AIU-045 needed a 6,189-word orchestration prompt
  and an 11,576-word analysis record.
- **Evidence:** AIU-055 tasks.md "Execution model", "Worker procedure"; verification.md T-09/
  T-10 rows. Anthropic multi-agent post: multi-agent ≈15× chat tokens; "most coding tasks
  involve fewer truly parallelizable tasks than research"; poor fit for shared context.
  Cognition: parallel subagents make conflicting implicit decisions. Agent-teams docs: "For
  sequential tasks, same-file edits, or work with many dependencies, a single session or
  subagents are more effective"; start with 3-5 teammates.
- **Label:** FACT (repo, sources); INFERENCE (generalization).
- **Confidence:** Medium-high (one successful run is not a trend; token cost not measured
  in repo).
- **Impact:** Speed: high for genuinely separable batches, negative for single features.
  Quality: risk of cross-task inconsistency (AIU-055 needed a whole-feature review for
  cross-task checks).
- **Proposed direction:** Default = one primary session per feature, subagents for read-only
  research and review. Use parallel worktree writers only when the owner asks or a T2 batch
  has ≥3 tasks with disjoint `writes` and no shared contract, max ~4 concurrent, shared
  resources (desktop smoke, preferences schema, migrations) serialized per formats.md.
  Workers should not each run the full smoke; the controller runs desktop smokes once on the
  integrated tree, workers run unit suites + build.
- **Verdict:** Adapt (keep the capability, narrow the trigger).
- **Security/supply-chain:** Workers pushing to main directly widens push authority to N
  agents; keep it owner-granted per run (as AIU-055 did), not standing.
- **Effort and upkeep:** Small doc change; saves tokens and desktop-lock contention.
- **KEEP:** formats.md ownership checks and "serialize shared resources"; "a worker claim is
  not completion"; controller verifies `merge-base --is-ancestor` before recording.

### B5-F5 — Per-task opus review produced mostly Minor findings; review should be per-feature and risk-triggered
- **Observation:** AIU-055 ran 11 per-task opus reviews (several with re-review rounds) plus
  one whole-feature review. Across them: one Important finding (T-10 flyout width ~247 px vs
  260 px, a real bug that a screenshot measurement or test could also catch); every other
  finding Minor; the whole-feature review found no Critical/Important. CONTRIBUTING itself
  requires only primary diff review for routine edits, and focused independent review for
  credential, destructive-data or privilege changes.
- **Evidence:** AIU-055 verification.md per-task review rows and T-12 row; CONTRIBUTING
  "Review and integration". Claude Code best practices: "A reviewer prompted to find gaps will
  usually report some, even when the work is sound… Chasing every finding leads to
  over-engineering." arXiv:2603.00539: richer review prompts raised GPT-4o false rejection of
  correct code from 35.9% to 87.9% on MBPP; 87% of false rejections were unsupported
  functional claims.
- **Label:** FACT (repo counts, sources); INFERENCE (proportionality).
- **Confidence:** Medium-high.
- **Impact:** Speed: high gain (11 reviews → 1). Quality: small risk, mitigated by keeping
  one integrated review and AC-driven tests.
- **Proposed direction:** One fresh-context review of the integrated diff per T1/T2 feature
  against its ACs; per-task review only when that task touches a T3 trigger (auth,
  credentials, persistence format, migration, destructive data, release/update path). One
  round, then targeted re-check of the fixed lines only (CONTRIBUTING already forbids an
  automatic full-review loop; the AIU-055 "up to three rounds" exceeded that spirit).
- **Verdict:** Adapt.
- **Security/supply-chain:** None; T3 review is unchanged and still blocking.
- **Effort and upkeep:** Small.
- **KEEP:** "Unresolved material findings block integration"; "zero findings is valid";
  focused independent review for credential/destructive/privilege changes.

### B5-F6 — Calibrate the reviewer: severity bar, evidence bar, convergence rule
- **Observation:** aiu-reviewer and convergence-review define verdict shape but not what
  counts as Important, nor a proof bar for behavior claims, nor a nit cap.
- **Evidence:** .claude/agents/aiu-reviewer.md; .agents/skills/convergence-review/SKILL.md.
  Claude Code REVIEW.md guidance: redefine Important, "report at most five nits", "behavior
  claims need a file:line citation", "after the first review, suppress new nits and post
  Important findings only". arXiv:2603.00539 mitigation: treat a reviewer's proposed fix as an
  executable counterfactual (test it) before acting.
- **Label:** FACT (sources); INFERENCE (fit).
- **Confidence:** High.
- **Impact:** Quality: fewer false positives and less over-engineering. Speed: fewer rounds.
- **Proposed direction:** Add four lines to the single reviewer definition: Important =
  violates an AC, the spec, a security/data boundary, or causes a reproducible defect;
  everything else Minor and non-blocking, at most five; each Important needs file:line plus a
  failing test, command output or concrete repro path; on re-review report only on the fixed
  lines and new Important issues. The implementer fixes an Important test-first (already
  repo practice), which doubles as the counterfactual check.
- **Verdict:** Adapt idea.
- **Security/supply-chain:** None.
- **Effort and upkeep:** Trivial.
- **KEEP:** read-only reviewer, fresh context, no implementation transcript, per-AC verdicts.

### B5-F7 — Use the built-in `/code-review` for correctness passes; reject the managed PR reviewer
- **Observation:** The repo works direct-to-main without PRs. Claude Code ships `/code-review`
  (fresh background subagent, effort-tunable; `low` = fewest false positives) at no install
  cost. The managed "Code Review" GitHub app is research preview for Team/Enterprise, needs
  PRs and a GitHub App with contents read + PR write, averages $15-25 per review, ~20 min, and
  never gates merges.
- **Evidence:** code.claude.com/docs/en/code-review (fetched 2026-10-08).
- **Label:** FACT.
- **Confidence:** High.
- **Impact:** Quality: a cheap second correctness lens (bugs) next to the AC-compliance
  review. Speed: neutral to positive.
- **Proposed direction:** For T1/T2, the primary runs `/code-review` (medium effort) on the
  integrated diff and an AC-compliance check (reviewer agent or the primary with the spec);
  for T3 add the focused independent review. Do not use `--fix` blindly; triage findings per
  F6. Ultrareview only on owner request (cloud upload of the branch).
- **Verdict:** Adopt `/code-review` (local); reject managed Code Review and CI review bots.
- **Security/supply-chain:** Local command, no install. Managed app/ultrareview send code to
  cloud review infrastructure and need a GitHub App — avoided.
- **Effort and upkeep:** None; one line in CONTRIBUTING.
- **KEEP:** CI `validate` and `windows-package` as the deterministic gate.

### B5-F8 — Evidence-before-claims is strong; give unattended runs a machine-checked done condition
- **Observation:** The repo's verification discipline is above typical practice: AC verdicts
  with command/commit, screenshots opened and compared, "tool claims are not execution",
  NOT_RUN honesty, Preview gate. What is prose-only is the stop condition of long autonomous
  runs; the agent decides "done".
- **Evidence:** docs/workflow/verification.md "Output", "Preview gate"; AIU-055 T-12 table.
  Claude Code best practices: "Give Claude a check it can run"; `/goal` sets a completion
  condition re-checked by a separate small model after every turn (judges only what the
  transcript shows; condition ≤4,000 chars; can include a turn cap); Stop hooks are the
  deterministic alternative.
- **Label:** FACT; INFERENCE (fit).
- **Confidence:** Medium.
- **Impact:** Quality: fewer premature "done" claims in unattended runs. Speed: fewer owner
  nudges.
- **Proposed direction:** Trial `/goal` on the next T2 run with a condition generated from
  the spec, e.g. "Presentation and Infrastructure suites pass, Release build 0 warnings,
  validator --final passes, demo launch smoke PASS, each AC-xx has a PASS/NOT_RUN row with a
  command, pushed commit is ancestor of origin/main; stop after 40 turns". Do not add a Stop
  hook running suites each turn (slow on this machine; Defender first-run latency).
- **Verdict:** Trial `/goal`; reject Stop-hook test gate for now.
- **Security/supply-chain:** Built-in; evaluator is a hook-system feature subject to
  workspace trust. No install.
- **Effort and upkeep:** Minutes per run; nothing persistent.
- **KEEP:** the entire verification.md "Output" contract and the change-based check matrix.

### B5-F9 — Agent definitions are run-specific and overlap the review skill
- **Observation:** All three `.claude/agents` describe themselves as AIU-045 workers; AIU-055
  had to embed a fallback ("if that type is not listed, general-purpose…"). Reviewer behavior
  is defined twice (aiu-reviewer, convergence-review) with different wording. Owner memory
  notes `.claude/agents` changes are not loaded mid-session.
- **Evidence:** .claude/agents/*.md frontmatter; AIU-055 tasks.md step 7.
- **Label:** FACT.
- **Confidence:** High.
- **Impact:** Quality: consistent review behavior. Speed: shorter briefs, no fallbacks.
- **Proposed direction:** Keep two feature-neutral definitions: `implementer` (worktree,
  test-first, write-set, report format — the current Worker procedure moved here) and
  `reviewer` (read-only, F6 calibration). Make convergence-review a thin pointer to the
  reviewer (or vice versa). Drop `aiu-simple-implementer` (model choice can be passed per
  call).
- **Verdict:** Adapt.
- **Security/supply-chain:** Keep reviewer tool list read-only (no Edit/Write/Agent).
- **Effort and upkeep:** Small; reduces per-feature prompt authoring.
- **KEEP:** reviewer's tool restriction; "never ask the owner, never push" for implementers
  unless the run grants push.

### B5-F10 — Agent teams and dynamic workflows: research/audit only, not implementation
- **Observation:** Agent teams are experimental, disabled by default, auto-approve teammate
  plans without lead review, cannot resume in-process teammates, and split panes do not work
  in Windows Terminal. Dynamic workflows (script-orchestrated subagents, resumable, size
  guideline default `medium` <10 agents, "Large workflow" warning >25 agents/1.5M tokens)
  suit audits, migrations and cross-checked research; they allow no mid-run user input.
- **Evidence:** code.claude.com/docs/en/agent-teams; /workflows docs.
- **Label:** FACT; INFERENCE (fit).
- **Confidence:** High.
- **Impact:** Speed gain for read-only fan-out (e.g. this Stage 1 audit); low value for
  feature implementation where owner checkpoints and desktop serialization dominate.
- **Proposed direction:** Use dynamic workflows (or plain parallel subagents) for read-only
  audits and research with adversarial cross-check; do not enable agent teams. Keep
  `ultracode` off by default (it plans a workflow for every substantive task).
- **Verdict:** Agent teams reject; dynamic workflows trial for read-only audits.
- **Security/supply-chain:** Built-in; workflow subagents inherit permission rules. Saved
  workflow scripts in `.claude/workflows/` would be repo code to review.
- **Effort and upkeep:** None unless saved.
- **KEEP:** "Keep one primary agent by default" (AGENTS.md).

### B5-F11 — Post-deploy owner checks are recorded NOT_RUN but have no closing step
- **Observation:** D-190 correctly moves live/manual checks after deployment and forbids
  blocking merge on them. Each feature then ends with a NOT_RUN "post-deploy owner check"
  row, but there is no defined place or trigger to record the outcome; AIU-045 did it ad hoc
  ("Post-install verification 2026-10-06").
- **Evidence:** AIU-055 verification.md "Not run"; AIU-045 spec "Exact next action";
  verification.md "Preview gate" last paragraph.
- **Label:** FACT; INFERENCE (accumulation risk).
- **Confidence:** Medium.
- **Impact:** Quality: closes the loop on live behavior. Owner involvement: one short prompt
  after updating instead of re-explaining what to check.
- **Proposed direction:** Each verification.md ends with a 3-5 item "Post-deploy check"
  list (what to look at, which log events confirm it). A small project skill
  `post-deploy-check` (owner-invoked, `disable-model-invocation`) reads the installed version
  and the sanitized app logs per AGENTS.md logging rules, walks the open lists of features
  shipped since the last check, and appends PASS/FAIL rows. No credentials read; owner-only
  trigger.
- **Verdict:** Adapt idea (small skill).
- **Security/supply-chain:** Must stay within logging privacy rules (no credentials, no raw
  provider bodies); read-only on the installed app's log folder.
- **Effort and upkeep:** ~1 short skill; low.
- **KEEP:** D-190 (never ask the owner to sign in to a dev build; never block merge/push).

### B5-F12 — Git policy text and parallel worktree practice disagree
- **Observation:** CONTRIBUTING says "Work directly on `main`… do not create new branches",
  while the owner routinely runs parallel worktree sessions (D-196 placeholders exist because
  of it) and AIU-055 workers commit on worktree branches before pushing to main. Agents must
  reconcile this each time.
- **Evidence:** CONTRIBUTING "Git policy" paragraphs 1 and 4; AIU-055 Worker procedure step 8.
- **Label:** FACT.
- **Confidence:** High.
- **Impact:** Speed and correctness of agent behavior (fewer contradictory readings).
- **Proposed direction:** State once: local worktree branches are allowed as short-lived
  isolation and are never pushed; integration is a merge of fresh `main` then push to
  `main`; numbering at merge per D-196.
- **Verdict:** Adapt (text fix).
- **Security/supply-chain:** None.
- **Effort and upkeep:** Trivial.
- **KEEP:** no force-push, no history rewrite, push status stated in every final reply.

## Proposed flow sketch

1. **Intake.** Owner message (or backlog item the owner selects). The primary inspects Git
   state and the affected code briefly, then states in one plan line: tier (T0-T3), intended
   result, acceptance checks. Visible UI change → 2-3 variants first (owner rule). Missing
   scope/security/destructive decisions → ask once.
2. **Spec, sized by tier.**
   - T0 fix: no spec; plan + evidence in the commit message.
   - T1 small feature: spec.md (≤ ~1 page, AC-xx) + verification.md. Bugs may use
     current / expected / unchanged headings.
   - T2 multi-part: as T1; tasks.md only if parallel workers are used (task blocks only;
     procedure lives in the implementer agent).
   - T3 auth/credentials/persistence/migration/destructive/release path: add design.md,
     security-lifecycle skill.
3. **Implement.** One primary session, test-first, research via read-only subagents. Parallel
   worktree workers only on owner request or a T2 batch with ≥3 disjoint write-sets, ≤4
   concurrent; desktop smokes serialized and run once by the controller on the integrated
   tree.
4. **Review (one pass, risk-based).** T0: primary diff review. T1/T2: `/code-review` on the
   integrated diff + AC-compliance check by the calibrated reviewer (F6). T3: plus focused
   independent review (convergence-review), blocking. After fixes: targeted re-check of
   fixed lines only.
5. **Verify.** Change-based matrix + Preview gate; AC rows PASS/FAIL/NOT_RUN/BLOCKED with
   command and commit; optional `/goal` encoding these as the stop condition.
6. **Merge.** Merge fresh `main`, assign AIU/D numbers, validator `--final`, push; reply
   states "Pushed to `main`" with hashes after `git fetch`.
7. **Post-deploy.** Green push publishes a Preview; owner installs; owner invokes
   `post-deploy-check`, which reads the installed version and sanitized logs and records the
   outcome against each feature's post-deploy list.

Drop: per-task independent reviews for routine tasks; per-task record commits; worker
procedure copied into every tasks.md; multi-round review caps above one round; run-specific
agent definitions. Keep: AC-driven specs, evidence vocabulary, validator, Preview gate,
D-190, security-trigger reviews, owner control of scope, UI variants, push-status reporting.
