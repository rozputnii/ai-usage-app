## Scope and method

- **What was read:** `origin/main` history at `4f32185` (2026-10-08 19:54). That is 450 commits from 2026-09-12 to 2026-10-08: 404 non-merge commits and 46 merges. I also read `.github/workflows/validation.yml`, `tools/windows/Publish-Preview.ps1`, the CONTRIBUTING Git policy, the registers (`docs/backlog.md`, `docs/decisions/accepted.md`) and the AIU-055 task and verification records.
- **CI data:** the last 200 GitHub Actions runs (2026-09-22 → 2026-10-08, all `Validation`, all on `main`). I used `gh run list` and `gh api …/runs/{id}/jobs` to get the timings of all 200 runs. I read the failed-step logs (`gh run view --log-failed`) for 15 of the 21 failed runs.

- **Labels:** **fact** means directly counted or quoted from the data. **inference** means my interpretation. I give confidence (high/medium/low) per finding.
- **Era split used below:**
  - "pre-CC" is 2026-09-12 → 10-04, when Codex/OMP/Astra were in use.
  - "CC-only" is 2026-10-05 → 10-08, Claude Code only.

## Findings

### A5-F1 — Every main push publishes a signed Preview, including docs-only pushes
- **Observation:**
  - `validation.yml` runs on `push: branches: [main]` with no `paths-ignore`.
  - The `preview` job runs whenever validation is green and `AIU_PREVIEW_ENABLED` is true.
  - `Publish-Preview.ps1` builds and signs a second MSIX and promotes the feed. It does not check whether product inputs changed.
  - CONTRIBUTING requires pushing "after each meaningful step".
- **Evidence:**
  - 161 Preview releases in 17 days; 37 on 2026-10-08 (tags `preview-2026.10.8xx.0`).
  - 96/197 pushes overall and 28/72 CC-only changed only docs.
  - The `record T-xx` commits (`87c34e6`, `991ff6d`, `b9a4889`, …) each triggered a full Preview.
- **Label:** fact. That docs-only pushes produce Previews identical in product content is an inference (version and build differ).
- **Confidence:** high.
- **Impact:**
  - Quality: the owner's installed app gets update churn with no product change. AIU-046 in-app update offers each one, which dilutes "post-deploy owner check" signals.
  - Speed: about 3 min of extra serialized CI per push. The preview queue reached 12 min during the 10-08 burst.
- **Proposed direction:** skip the `preview` job (or skip promotion) when the diff since the last published Preview touches no product inputs, using a path filter or a check inside `Publish-Preview.ps1`. Keep `validate` on every push. Optionally batch doc record commits into the merge push.
- **KEEP:** automatic Preview on green product pushes (owner decision 2026-10-06), immutable release assets, and the signed-feed gate after `validate` and `windows-package`.

### A5-F2 — CI runs only after code is already on `main`; branches and PRs get no CI
- **Observation:**
  - Work happens in `.claude/worktrees/*` branches that are merged locally and fast-forward-pushed to `main`.
  - `pull_request` is a trigger, but there are 0 PRs, and branch pushes do not trigger CI.
  - A red CI run therefore means `main` is red. The Preview for that push is blocked, and the next push has to fix it.
- **Evidence:**
  - 200/200 runs have `headBranch=main`; `gh pr list` is empty; only 3 remote branches.
  - Example: on 10-03, six consecutive red pushes from the DiagnosticCrashTests flake (runs 37123301624 … 37163134018) before it was fixed on 10-06 (`13814e1`).
- **Label:** fact; impact is inference.
- **Confidence:** high.
- **Impact:**
  - Quality: CC-only red rate is low (2.7 %), so the practical risk is small now.
  - Speed: local checks are the real gate, which is fast and acceptable for a solo owner.
- **Proposed direction:** no PR workflow (it adds owner involvement). Keep local `--final` validation plus suites before push, which already removed doc-validation reds (see F3). Consider one cheap pre-push hook that runs the validator.
- **KEEP:** the post-push CI as the clean-machine gate before Preview publication.

### A5-F3 — Doc-validation reds disappeared after the CC switch; the remaining CI value is clean-machine and flake detection
- **Observation:**
  - 10 of 21 failures were "Canonical document validation", all from pre-CC WIP or non-conventional pushes. Examples: `810a11c`, `dfd83f8` ("AIU-035 WIP"), `b91da5d`/`4dc291b`/`5c60dae` (wip AIU-043), `c9dff85`.
  - After 10-05 there is exactly one doc failure. Run 37298379475 (`069095a`) had BROKEN_LINK into the ignored `.ai-usage-local` root: the files existed locally, so local validation passed.
  - That gap was then closed in the validator (`8f05989` "report links into the ignored .ai-usage-local root as broken").
- **Evidence:** run ids above. Diagnostics codes: REQUIRED_METADATA, INVALID_STATUS, DONE_WITHOUT_EVIDENCE, BROKEN_LINK.
- **Label:** fact; that the CC-only workflow runs `--final` locally is inference from D-196 and the commit bodies.
- **Confidence:** high.
- **Impact:** quality positive. CI now mainly catches environment-dependent problems: untracked local files and timing flakes.
- **Proposed direction:** keep the validator in CI. No added checks needed.
- **KEEP:** validator regressions plus canonical validation `--final` in CI.

### A5-F4 — Timing-flaky tests are the dominant real CI failure class and took days to fix
- **Observation:**
  - `DiagnosticCrashTests.ForcedKillLeavesPriorRecordsAndUnknownExitWithoutInventedCritical` failed in 6 runs on 2026-10-03.
  - The root cause, from the commit body, was that `WaitForExitAsync` returns before Windows has released the killed probe's handles. It was fixed 3 days later in `13814e1` during the AIU-045 fix run.
  - `LiveLedgerSourceTests.PauseWaitsForAWaitingSignIn` failed once (run 37541061670, 10-06 22:30) and was fixed about 2 h later (`1eb8c7c` "wait for the snapshot rebuild").
  - `FileDiagnosticsTests.EventsAreJsonAndExceptionValuesNeverReachDisk` failed once (37149521238).
- **Evidence:** run ids above, plus 8 flaky failures out of 11 test failures.
- **Label:** fact.
- **Confidence:** high.
- **Impact:**
  - Quality: flakes on main train agents to rerun or ignore red.
  - Speed: blocked Previews for a day.
- **Proposed direction:** when CI is red, triage flake vs regression the same day. Record each flake in a single short known-flakes list (or the task doc) with its fix commit. Prefer deterministic waits over sleeps, as both fixes did.
- **KEEP:** the fix style (`13814e1`, `1eb8c7c`): explain the race, then wait on the actual condition.

### A5-F5 — Parallel AIU-055 run: fast, review-gated, but produced ~50 commits and 11 leftover ~450 MB worktrees in 2 h
- **Observation:**
  - AIU-055 went from spec and numbering at 17:40 (`7cc7d7e`, `22e1324`) to completion at 19:54 (`4f32185`): 11 tasks in about 2 h 15 min.
  - The pattern per task:
    1. feat in an `agent-*` worktree
    2. an `aiu-reviewer` (opus) review, followed by a minor fix commit within 5–15 min
    3. "Merge origin/main into worktree-agent-X"
    4. fast-forward of main
    5. a separate "docs(AIU-055): record T-xx" commit
  - Totals: 11 feat, 8 fix, 1 test, 11 record, about 17 merges.
  - The 11 subagent worktrees stay registered after merge, at 430–460 MB each.
- **Evidence:**
  - `git log 22e1324..4f32185`; AIU-055 `verification.md` rows for T-01…T-11 (each "independent review Approve").
  - Worktree list; `du`.
- **Label:** fact; that the per-task record commits add little value is inference.
- **Confidence:** high for counts, medium for the value judgment.
- **Impact:**
  - Quality: positive. Each task was red-to-green with its own review.
  - Speed: positive overall.
  - Clutter: main history is about 60 % bookkeeping (merges plus records), each record push triggers a Preview (F1), and there is about 5 GB of stale worktrees.
- **Proposed direction:**
  - Fold the task record into the task's integration commit, or batch records into one commit per wave.
  - Remove a subagent worktree once its branch is merged into main. The cleanup is safe because merge into `origin/main` is verifiable; it needs the owner's or tool's cleanup action, not this lane.
  - Possibly merge `main` into worktrees only once, right before integration.
- **KEEP:** per-task independent review, red-first smokes, write-set ownership in `tasks.md`, the whole-feature final review.

### A5-F6 — Smoke harness is the main source of rework at integration, sometimes because of the owner's installed app
- **Observation:**
  - T-09 evidence says: "post-merge Ledger launch smoke FAIL 2/3 from the owner's tray icon, smoke fix assigned to T-10".
  - The T-10 chain was:
    - `29f0fb3` feat
    - `4f2b8a1` (tray content width inside the window frame, plus the smoke finding its icon when the overflow stays open)
    - `918b1cd` (smoke finds the overflow chevron by id and prefix and opens it only when closed)
  - The installed app's tray icon and the desktop state contaminate the dev smoke.
  - Earlier AIU-045 smoke-robustness commits: `02e0ca8`, `11645ac` (resolve the Ledger window afresh), `4c32153` (invoke buttons only once enabled), `e40c76d` (bring Close settings into view), `03e6d5b` (type Enter so History clicks on release).
  - `3b643d7` reports a smoke rerun "after a focus steal by another window".
- **Evidence:**
  - 77 commits touch `tests/windows/AiUsage.Windows.Tests`.
  - Smoke share of line churn rose from 3 % overall to 7 % CC-only.
  - `LedgerSmoke.cs` 23 commits, `ShellSmoke.cs` 15, `AuditWindows.cs` 14.
- **Label:** fact (quotes); "main source of rework" is inference.
- **Confidence:** medium.
- **Impact:**
  - Quality: a smoke that depends on the owner's desktop can false-fail. Historically it also false-passed: `e5013fa`, the blank tray icon at >100 % scaling, where tooltip-based checks "passed while the owner saw a blank slot".
  - Speed: integration rework.
- **Proposed direction:**
  - Give the smoke a deterministic tray locator that ignores the installed package's icon, and document "installed app running" as a known interference.
  - Keep smokes few and targeted.
  - Check visuals with screenshots where a tooltip or automation check can pass while the rendering is wrong (T-02 and T-07 already do).
- **KEEP:** red-then-green smokes per UI task; screenshot artifacts in the evidence.

- **Evidence:** commit bodies; `accepted.md` entries D-191 … D-206 ("Owner direction, 2026-10-07/08, in conversation …").
- **Label:** fact for the list. The classification (spec or design intent: about 5; validation gap: 2; test gap: 0–1) is inference.

### A5-F8 — Merge-time numbering (D-196) works but costs a numbering commit plus a register conflict per feature, and has already misfired once
- **Observation:**
  - Before D-196, parallel worktrees collided:
    - `8bac814` "main had assigned AIU-046 and D-188 to other work, so … becomes AIU-048 with decision D-189"
    - D-196's own text cites a D-195 collision on 10-08.
  - After D-196 (10-08 10:49), each merge adds a "number the item / assign D-xxx" commit: `d8b5efa`, `65f7fcb`, `902b196`, `b81ef9e`, `22e1324`, and `10477c3`.
  - Each merge also resolves append-at-end conflicts in `backlog.md` and `accepted.md`: `727c1f0` (36 combined-diff lines), `d104c5b` (32), `8bac814` (64).
  - The mechanical replacement once overreached: `d8b5efa` replaced the literal `D-NEW` in D-196's own rule, which was restored in `a0f0d22`.
- **Evidence:** commits above; 0 duplicate `### D-` or `## AIU-` headers on main now.
- **Label:** fact.
- **Confidence:** high.
- **Impact:**
  - Quality: positive. There are no collisions on main and CI `--final` rejects placeholders.
  - Speed: a small but per-feature cost, plus register conflicts on two hot files (124 and 47 commits).

### A5-F10 — CONTRIBUTING's Git policy no longer describes actual practice
- **Observation:** CONTRIBUTING says:
  - "Work directly on `main` by default … do not create new branches"
  - "Keep one active feature unless the owner explicitly requests a bounded batch"
  
  Actual CC-only practice is 37 branches in 4 days, 30 merges of origin/main into worktree branches, and 11 concurrent subagent worktrees. D-196 itself acknowledges that "the owner often runs tasks in parallel worktrees".
- **Evidence:** CONTRIBUTING.md lines 26–64; branch list.
- **Label:** fact for both texts; drift is inference. The branches are created by the Claude Code desktop worktree feature, which may count as owner-requested.
- **Confidence:** medium-high.
- **Impact:** agents read contradictory rules (main-only vs worktrees), which risks hesitation or wrong integration choices.
- **Proposed direction:** rewrite the Git policy to the actual flow: worktree branch, merge fresh main, renumber, local checks, fast-forward push to main, then remove the worktree. Drop the main-only wording.
- **KEEP:** never force-push or rewrite history; push status reporting (2026-10-08); save points never upgrade NOT_RUN or FAIL.
