## Findings

### B3-F1 — Native Claude Code LSP (`csharp-lsp` + `csharp-ls`) is the best code-intelligence candidate
- **Observation:** Claude Code has a first-party `LSP` tool. With a language-server plugin it reports diagnostics automatically after every edit and offers definition, references, hover/type, document/workspace symbols, implementations and call hierarchy. Anthropic maintains `csharp-lsp` in the official marketplace. That plugin runs the community `csharp-ls` server (Roslyn and MSBuild based, MIT, single owner razzmatazz, about 1,000 stars, monthly releases: 0.25 in 2026-06, 0.26 in 2026-07, 0.27 in 2026-08, 0.28 on 2026-09-13). It requires the .NET 10 SDK, supports `.slnx` (since 0.18), and recent releases fix Windows URI casing and platform-TFM handling, which matter for a `net10.0-windows…`/x64 WinUI project. At about 37k lines, Grep/Read already finds most things. The concrete gain is **type errors after each edit without running a build** (the WinUI project build is the slowest local loop) and precise references for renames across the Core, Infrastructure and Windows boundaries.
- **Evidence:** https://code.claude.com/docs/en/plugins/code-intelligence ; https://code.claude.com/docs/en/tools-reference#lsp-tool-behavior ; https://github.com/razzmatazz/csharp-language-server (README, docs/troubleshooting.md, CHANGELOG.md) ; local marketplace entry `csharp-lsp` 1.0.0 (command `csharp-ls`, `.cs` only); all accessed 2026-10-08.
- **Label:** Fact (capability, maintenance); Hypothesis (fit with this WinUI solution).
- **Confidence:** Medium. Fit risks: (a) csharp-ls loads the solution in the current directory, but this repo's root has none (`src/windows/AiUsage.slnx`), and the plugin passes no `--solution` argument. With no solution in the root it is expected to fall back to discovering projects, which would also pick up tests, tools and spikes. This is unverified. (b) WinUI XAML code-behind (`InitializeComponent`, `x:Name` fields from the XAML compiler) may not be produced in a design-time load, which could give false "does not exist" diagnostics in the 6 XAML-backed classes. (c) Memory and first-load time in each parallel worktree session.
- **Impact:** Quality: catches compile errors earlier and gives semantically correct references, for example around opaque provider types. Speed: fewer edit→build→fix cycles, most visible in `AiUsage.Windows`.
- **Proposed direction:** A time-boxed trial on one ordinary task. Install `csharp-ls` as a global .NET tool from NuGet and enable `csharp-lsp@claude-plugins-official` at user scope. No repository file changes. Acceptance checks: diagnostics line appears after an edit in Core, Infrastructure and Windows; no false errors in XAML code-behind; `references` works from a test project into `src`; memory stays acceptable with 2 worktrees. If (a) or (b) fails, either accept Core/Infrastructure-only value or use the fallback in B3-F2. Never treat LSP diagnostics as verification evidence. The README build and test commands remain the checks of record.
- **Verdict:** **Trial** (adopt if the acceptance checks pass).
- **Security/supply-chain:** csharp-ls is third-party code that runs MSBuild evaluation of the repo, which is the same trust level as `dotnet build`. It installs once from nuget.org. Pin a version (`dotnet tool install -g csharp-ls --version 0.28.0`) and update deliberately. The plugin itself is Anthropic-maintained and has no network role. The LSP tool is read-only. There is no credential exposure beyond what a build already has. Analyzers stay off by default.
- **Effort and upkeep:** About 15 minutes to install and trial. Upkeep is an occasional `dotnet tool update`. It is a user-level setting, so it adds no repository complexity.
- **KEEP:** Grep/Read as the primary navigation; README commands as the verification of record.

### B3-F2 — Reject Serena and Roslyn MCP servers; keep Microsoft's `roslyn-language-server` only as an LSP fallback
- **Observation:** Serena (oraios, about 30k stars, v1.7.0 on 2026-08-09, GPL-3.0 application) uses Microsoft's Roslyn LS for C#. On Windows its C# support **requires PowerShell 7 (`pwsh`)**, which this host does not have (owner memory: "no pwsh 7"). The official-marketplace `serena` plugin launches `uvx --from git+https://github.com/oraios/serena`, which is unpinned HEAD of a git repo fetched at every start. Serena's own README warns that marketplace install commands are outdated. Serena replaces native file/search tools with its own symbol-level tools, writes memories and overlaps the native LSP tool. Its README places the benefit in "larger and more complex codebases". Roslyn MCP servers: SharpLensMcp (single maintainer, v1.6.3 on 2026-08-16, about 6.6k downloads, 58 tools, needs manual `sync_documents` after edits made outside it). carquiza/RoslynMCP was last pushed 2025-06; other Roslyn MCP repos have fewer than 35 stars. Microsoft publishes `roslyn-language-server` (owners Microsoft/RoslynTeam, prerelease 5.12.0-1.26475.2, 2026-09-30) as a .NET tool, but no official Claude Code plugin wraps it.
- **Evidence:** https://github.com/oraios/serena (README; docs/01-about/020_programming-languages.md) ; local marketplace `external_plugins/serena/.mcp.json` ; https://www.nuget.org/packages/SharpLensMcp ; https://github.com/carquiza/RoslynMCP ; https://www.nuget.org/packages/roslyn-language-server ; `gh api` metadata; all accessed 2026-10-08.
- **Label:** Fact.
- **Confidence:** High.
- **Impact:** Adopting these would add tool-surface and context cost, a sync burden and supply-chain risk for little gain over B3-F1 at 37k lines.
- **Proposed direction:** Do not add. If the csharp-ls trial fails on WinUI loading, the only fallback worth considering is a small local plugin `.lsp.json` pointing at Microsoft's `roslyn-language-server`. That is additional configuration, so ask the owner first under the simplicity rule.
- **Verdict:** **Reject** (Serena, SharpLensMcp, RoslynMCP). **Adapt idea** (Microsoft Roslyn LS as a conditional LSP fallback only).
- **Security/supply-chain:** Serena's plugin executes unpinned git HEAD through uvx (Python), which is high supply-chain risk. Roslyn MCP servers are single-maintainer .NET tools running in-process MSBuild with write/refactor tools.
- **Effort and upkeep:** Serena: Python/uv + pwsh 7 install, per-project config and memories. Not justified.
- **KEEP:** One code-intelligence mechanism (native LSP), not two.

### B3-F3 — .NET build/test through MCP is not better than the CLI already in use; use the xUnit v3 runner's own structured output and filters
- **Observation:** No official Microsoft MCP server wraps `dotnet build`/`dotnet test`. Microsoft ships MCP *templates*, and the NuGet MCP server only covers package lookup and management. This repo already runs tests as xUnit v3 executables (`dotnet run --project … -- -noLogo`). The local runner help confirms built-in options that give an agent what a "test MCP" would: `-reporter quiet` (failures only), `-reporter json`, `-method`/`-class`/`-trait`/`-filter` for focused reruns, `-stopOnFail`, `-list … /json`, and result files `-ctrf`/`-trx`/`-xml`/`-html`. The validator already emits `--json`. With 11 centrally pinned packages, `dotnet list package --vulnerable --outdated` covers dependency checks without the NuGet MCP server.
- **Evidence:** local `tests/windows/AiUsage.Presentation.Tests/bin/Release/net10.0/AiUsage.Presentation.Tests.exe -?` (2026-10-08) ; README "Local checks" ; https://learn.microsoft.com/dotnet/ai/get-started-mcp ; https://www.nuget.org/packages/NuGet.Mcp.Server (2026-10-08).
- **Label:** Fact (options exist); Inference (speed benefit).
- **Confidence:** High.
- **Impact:** Speed: `-reporter quiet` plus a focused `-class`/`-method` rerun reduces output tokens and rerun time after a failure. Quality: a `-ctrf` or `-trx` file is a durable, parseable artifact for verification records.
- **Proposed direction:** Add no MCP. Optionally, B-lane synthesis may propose one README line under Local checks: "for a focused rerun append `-class <FQN>` or `-method <FQN>`; `-reporter quiet` prints failures only". This is documentation only. Lane A/B owners decide.
- **Verdict:** **Reject** (build/test MCP, NuGet MCP). **Adopt idea** (document existing runner flags).
- **Security/supply-chain:** No change. This avoids a new server process with shell access.
- **Effort and upkeep:** A one-line doc change, nothing to maintain.
- **KEEP:** `dotnet run` test executables, validator `--json`, `git diff --check`.

### B3-F4 — Keep the FlaUI smoke harness; reject Windows-MCP-style desktop-control servers
- **Observation:** The repo's harness (`tests/windows/AiUsage.Windows.Tests`, 3,645 lines, xUnit v3 + FlaUI.UIA3) is deterministic. It requires an unlocked desktop and that the test process owns the foreground, and it fails with explicit `BLOCKED:` messages (`DesktopTestEnvironment`). It uses an isolated `AIU_DEVELOPMENT_STATE_DIRECTORY`, a `demo` mode and an evidence directory, and drives real mouse input (about 175 `Click`/`Mouse`/`Keyboard` uses vs about 70 pattern uses). That is a deliberate proof of real interaction. CursorTouch/Windows-MCP (about 8.3k stars, v0.8.7 on 2026-09-30, MIT, Python 3.13 via `uvx`) exposes Click/Type/Snapshot plus **PowerShell, Registry, FileSystem, Process, Clipboard** tools. Its README states it "operates with full system access and can perform irreversible operations". Anonymous telemetry to PostHog is **on by default** (`ANONYMIZED_TELEMETRY`). The FlaUI ecosystem's MCP wrappers (FlaUiScreenReaderMcp 0.0.4 PoC, WpfPilot, WinApp MCP and others) are small, self-described and unaudited. FlaUI itself: v5.0.0 (2025-02), repo active 2026-08.
- **Evidence:** https://github.com/CursorTouch/Windows-MCP (README, 2026-10-08) ; `gh api repos/CursorTouch/Windows-MCP`, `repos/FlaUI/FlaUI` (2026-10-08) ; https://www.nuget.org/packages/Rotbarsch.FlaUiScreenReaderMcp ; local harness source.
- **Label:** Fact.
- **Confidence:** High.
- **Impact:** A desktop-control MCP would not improve the repeatable evidence the verification policy requires ("Tool claims and generated reports are not test execution"). It would add a broad, always-on control channel next to an app that holds provider credentials.
- **Proposed direction:** Keep FlaUI as the single scripted UI test layer. For exploratory "look at the running app" needs, see B3-F5 and B3-F6.
- **Verdict:** **Reject** (Windows-MCP, FlaUI-MCP wrappers).
- **Security/supply-chain:** Windows-MCP has full system access including registry and shell outside Claude Code's Bash permission rules and sandbox, sends telemetry by default, has an optional remote HTTP mode, and installs a Scheduled Task (`windows-mcp install`). It conflicts with "never change host trust/settings" and "never read source CLI credentials" unless it is heavily restricted.
- **Effort and upkeep:** Python/uv toolchain plus config. Not justified.
- **KEEP:** FlaUI harness, `RequireUnlockedDesktop`/`RequireOwnedForeground` gates, BLOCKED/NOT_RUN reporting.

### B3-F5 — Microsoft `winapp ui` CLI is a credible, first-party exploratory UIA tool; trial its read-only verbs only
- **Observation:** Microsoft's Windows App Development CLI (microsoft/winappCli, MIT, **Public Preview**, about 1.3k stars, releases v0.5 on 2026-07-20 through v0.7.1 on 2026-10-01) has `winapp ui inspect | search | get-property | screenshot | wait-for | invoke | set-value | click | send-keys | record`, each with `--json` output. It is designed for agents, and it is a **CLI, not an MCP server**, so it fits Claude Code's Bash/PowerShell permission model. Microsoft documents that pattern verbs (inspect, search, invoke, set-value) are "headless/locked-session friendly", while input-injecting verbs need an unlocked desktop. It also publishes the engine as NuGet libraries. The repo ships an optional Claude Code plugin (`winappcli`), and the related `winui@awesome-copilot` plugin includes `winui-setup`, which turns on Developer Mode, and cert/sign commands that create a `devcert.pfx` with default password "password" and add it to `CurrentUser\My`. Telemetry is on by default in signed releases; the opt-out is `WINAPP_CLI_TELEMETRY_OPTOUT=1`.
- **Evidence:** https://learn.microsoft.com/windows/apps/dev-tools/winapp-cli/ui-automation ; https://learn.microsoft.com/windows/apps/develop/ai-assisted/testing ; https://github.com/microsoft/winappCli (README, docs/telemetry.md dated 2026-08-25, docs/security.md) ; `gh api repos/microsoft/winappCli/releases`; all accessed 2026-10-08.
- **Label:** Fact (capabilities, risks); Hypothesis (value here).
- **Confidence:** Medium.
- **Impact:** Speed: an agent can answer "is control X present, enabled, named correctly?" against a running `--demo` build in seconds without writing a FlaUI test. That helps when drafting the 2–3 UI design variants the owner requires and when debugging a failing smoke selector (`inspect --json` shows the real AutomationIds). Quality: it is exploratory only. It never replaces FlaUI smoke as evidence.
- **Proposed direction:** Trial `winget install Microsoft.winappcli` (pinned version) with `WINAPP_CLI_TELEMETRY_OPTOUT=1`, using only `ui inspect/search/get-property/screenshot/wait-for` against the unpackaged `--demo` app with an empty `AIU_DEVELOPMENT_STATE_DIRECTORY`. Do **not** install the WinUI/winappcli plugins. Do not run `winui-setup`, `cert`, `sign` or Developer Mode commands, because these change host trust/settings and the repo already owns signing in `Build-Package.ps1`. Measure one real debugging use before any documentation change.
- **Verdict:** **Trial** (narrow, owner-approved, user-level install).
- **Security/supply-chain:** Microsoft-signed, MIT, but preview with fast churn. It can read any window's UIA tree, so scope it to the AiUsage process (`-a`/`-w`). The installed product app shows account data, so target the `--demo` dev build only. Telemetry must be opted out.
- **Effort and upkeep:** About 10 minutes to install. Preview CLI flags may change, which is why it is kept out of repo scripts until stable.
- **KEEP:** FlaUI as the scripted layer, with no second test framework in the repo.

### B3-F6 — Claude Desktop computer use: allowed only as an owner-present, demo-mode visual aid, never as evidence
- **Observation:** Claude Code Desktop on Windows offers computer use (research preview, Pro/Max, **off by default**). It uses per-app "Allow for this session" approval and category tiers (IDEs/terminals click-only, browsers view-only, others full control) plus a denied-apps list. It acts on the real desktop, outside the Bash sandbox. CLI computer use is macOS-only. This session already lists a computer-use skill.
- **Evidence:** https://code.claude.com/docs/en/desktop ; https://code.claude.com/docs/en/computer-use (2026-10-08).
- **Label:** Fact; Inference (fit).
- **Confidence:** Medium.
- **Impact:** It could let an agent visually sanity-check layout for design variants. It adds little over B3-F5 screenshots plus FlaUI evidence, and it holds the owner's desktop.
- **Proposed direction:** Keep it off by default. If used, approve only the AiUsage dev window for one session and run `--demo` with isolated state. Add the installed AiUsage package, browsers and any provider CLIs or sign-in windows to Denied apps. Never use it for sign-in (AGENTS: "never sign in automatically") or for post-deploy checks of the installed app (D-190 keeps those with the owner).
- **Verdict:** **Adapt idea** (narrow, optional; no standing enablement).
- **Security/supply-chain:** Screenshots of the real desktop can capture account identities and quota data, and full-control apps can be driven arbitrarily. First-party, no new supply chain.
- **Effort and upkeep:** None unless used.
- **KEEP:** Owner-only manual and live checks after deploy (D-190).

### B3-F7 — GitHub: keep `gh` CLI; reject the GitHub MCP server
- **Observation:** github/github-mcp-server is first-party and very active (about 33k stars; v1.13 on 2026-10-01 through v2.0.2 on 2026-10-08, three releases in three days around a 2.0 typed-output change). The official-marketplace `github` plugin connects to the **remote** endpoint `https://api.githubcopilot.com/mcp/` with `Authorization: Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}`, so it needs a PAT in an environment variable. The repo's GitHub needs are narrow: push to `main`, watch CI (`validate`, `windows-package`), read run logs, and owner-authorized dispatch or release. `gh` 2.100.0 (2026-09-03) is installed and keyring-authenticated, has `--json/--jq` structured output, and is already the instructed tool. The desktop session also has native PR/CI monitor tools (`ccd_pr`).
- **Evidence:** https://github.com/github/github-mcp-server/releases ; local marketplace `external_plugins/github/.mcp.json` ; `gh --version` (2026-10-08).
- **Label:** Fact.
- **Confidence:** High.
- **Impact:** No quality or speed gain for a solo push-to-main flow. It adds many tools, another credential, and a remote hop.
- **Proposed direction:** None. If PR-heavy work appears later, revisit with `--read-only` and a toolset allowlist.
- **Verdict:** **Reject.**
- **Security/supply-chain:** A long-lived PAT in an environment variable is visible to every child process, whereas `gh` keeps credentials in the OS keyring. Write tools such as issue/PR/merge would sit beside the CONTRIBUTING rule that remote actions beyond push need owner authorization. Fast release churn.
- **Effort and upkeep:** PAT rotation plus plugin updates. Not justified.
- **KEEP:** `gh run list/view/watch --json`, the native Git policy.

### B3-F8 — Microsoft Learn MCP (already connected): adopt explicit usage guidance, not more tooling
- **Observation:** Learn MCP (`https://learn.microsoft.com/api/mcp`, no auth, free, tools `microsoft_docs_search`, `microsoft_code_sample_search`, `microsoft_docs_fetch`) is already connected at user level and worked in this lane. It returned current `winapp ui` and WinUI guidance that a generic web search did not. MicrosoftDocs notes that Claude models "sometimes skip MCP tools unless prompted", so explicit instructions help. Large pages exceed the tool-result limit and spill to a file (observed here: 83,904 characters), so search first and then fetch selectively. A `microsoft-docs` plugin and a Learn CLI also exist. Installing them on top of the connector would duplicate tools; Microsoft documents a similar duplicate-server conflict in Visual Studio.
- **Evidence:** https://github.com/MicrosoftDocs/mcp (README) ; this lane's live calls (2026-10-08).
- **Label:** Fact.
- **Confidence:** High.
- **Impact:** Quality: grounded WinUI / Windows App SDK / MSIX / .NET 10 API answers newer than model training. Speed: fewer speculative web fetches.
- **Proposed direction:** Add one line under AGENTS.md "Read by task", for example: "Windows App SDK, WinUI, MSIX, .NET or Windows API questions: search Microsoft Learn (docs/code-sample search, then fetch); queries must not contain provider payloads, account identifiers, credentials or local paths." Do not use it for provider quota or auth contracts; those stay with the provider-evidence skill and `docs/providers/`. Fall back to WebFetch of learn.microsoft.com if the connector is unavailable. Do not add the plugin or CLI.
- **Verdict:** **Adopt** (guidance only).
- **Security/supply-chain:** Queries leave the machine to Microsoft (egress). Returned content is data, not instructions. The service needs no credential.
- **Effort and upkeep:** One line. The connector's availability is outside the repo, so the line must say "when available".
- **KEEP:** provider-evidence skill as the authority for provider contracts.

### B3-F9 — Reduce the ambient MCP surface in repo sessions (Desktop Commander, personal connectors)
- **Observation:** Repo sessions currently load the user-level Desktop Commander plugin MCP (DesktopCommanderMCP v0.2.52, 2026-09-29; it failed to connect this session) and claude.ai connectors for Gmail, Calendar, Drive and design tools (Asana/Atlassian/Figma/… awaiting auth). Desktop Commander offers shell processes and filesystem tools. Its own README states that `allowedDirectories` "only restricts filesystem operations, not terminal commands", warns that Claude may try to change that setting, and has optional telemetry. Its commands do not pass through Claude Code's Bash/PowerShell permission rules or sandbox. The personal mail and drive connectors are untrusted-content and data-egress channels with no repository use. Claude Code supports per-project disabling (`/mcp` toggle → `disabledMcpServers` keyed per project in `~/.claude.json`), `deniedMcpServers`, and `disableClaudeAiConnectors: true` in project settings. The docs say that last setting does **not** govern desktop-app local sessions, which receive connectors from the host.
- **Evidence:** https://code.claude.com/docs/en/mcp ; https://github.com/wonderwhy-er/DesktopCommanderMCP (README) ; session MCP status (2026-10-08).
- **Label:** Fact; Inference (risk weighting).
- **Confidence:** Medium-high.
- **Impact:** Quality and security: removes a shell path that bypasses the repo's permission and sandbox controls, and fewer injection-capable data sources. Speed: smaller deferred-tool catalogue and fewer failed-connection notices.
- **Proposed direction:** Owner decision. Toggle Desktop Commander and the personal connectors off for this project through `/mcp`, or the desktop app's connector settings, since the project setting does not apply there. Keep Learn MCP. This is user-level configuration with no repository change.
- **Verdict:** **Adapt** (owner-applied, per-project disable).
- **Security/supply-chain:** Positive. It narrows the attack surface around a credential-handling app.
- **Effort and upkeep:** A few minutes, once.
- **KEEP:** Native Bash/PowerShell with Claude Code permissions as the only shell path.
