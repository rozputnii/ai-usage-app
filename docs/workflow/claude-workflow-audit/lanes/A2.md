# Lane A2 — Work records

## Scope and method

**Sources read (fact):** `docs/backlog.md` (627 lines, 11,030 words), `docs/product/goals.md`, `docs/workflow/formats.md`, `CONTRIBUTING.md` (Records, Git policy), `tools/AiUsage.ProjectValidation/ProjectValidator.cs` (267 lines) and `tests/AiUsage.ProjectValidation.Tests/ValidatorTests.cs` (29 facts/theories), `.github/workflows/validation.yml` (triggers only), decisions D-180 to D-206 in `docs/decisions/accepted.md`. All 38 spec folders were measured; the specs, tasks and verification records of AIU-046 to AIU-055 and AIU-038 were read in part or in full.

**Method:**
- Line and word counts per file and folder.
- Backlog parsed by item, status and field (`work/A2/backlog_stats.py`).
- Historical sizes of the backlog and the specs from `git rev-list --before` snapshots.
- Commit classification by touched paths and by subject (405 non-merge commits from 2026-09-12 to 2026-10-08; all repository history falls inside the last 30 days).
- Cross-references to each spec file from tracked files outside its own folder (`work/A2/xref2.py`).
- Status consistency between specs and backlog, and AC coverage between specs and verification.
- Transcript tool-call counts: 166 `.jsonl` files in 24 project directories, 2026-09-15 to 2026-10-08, excluding this audit. These are counts only and no content was copied (`work/A2/reads.py`, `bash.py`).

**Not covered:**
- `Read` counts miss reads made through Bash (`cat`, `sed`, `git show`). Bash commands that mention the paths were counted, but those mentions are ambiguous.
- I did not run the validator. Running it would build into the repository's `bin` and `obj` folders, so its runtime is NOT_RUN.
- I did not read the full contents of `docs/decisions`, `docs/providers` or the skills. They belong to other lanes and are cited here only where they duplicate records.
- I did not measure CI duration.

## Findings

### A2-F1 — The backlog is about 80 % closed history and grows about 16 lines a day
- **Observation:** Of 55 items, 34 are done and 1 is dropped. Done items take 410 of 589 item lines and 7,665 of 9,848 item words (78 %). Live items (13 idea, 5 research-needed, 1 paused, 1 review) take about 1,840 words. Each new item adds 160 to 260 words. Items use 37 distinct field names, 20 of them ad-hoc `*-note` fields (scope-note 20 times, outcome-note 12, completion-note 11, registration-note 14, and others).
- **Evidence:** backlog.md was 218 lines / 1,551 words on 2026-09-13, 425 / 6,811 on 2026-09-30 and 627 / 11,030 on 2026-10-08. 124 commits touched it, and transcripts show 31 Edits against 16 Reads of it.
- **Label:** fact (counts); inference (cost per read ≈ 14–15k tokens at 1.33 tokens/word).
- **Confidence:** high.
- **Impact:** Quality: done-item prose sits next to live work, and stale outcomes mislead (see F6). Speed: every agent that loads the backlog pays about 15k tokens, most of it history.
- **Proposed direction:**
  - Keep only live items in full.
  - Replace each done or dropped item with a one-line index row: ID, title, goal, done date and spec/verification link.
  - The detailed outcome and notes already live in the spec folder.
  - Use a fixed small field set and drop free-form `*-note` fields; one optional `note` is enough.
- **KEEP:** IDs, status, depends_on, goal and the evidence link for done items, which the validator requires and which keep traceability.

### A2-F2 — One owner choice is written down three or four times; one completion three times
- **Observation:** For AIU-046 to AIU-055, the owner's request and chosen variant appear in:
  - spec `approval_basis` (68–180 words);
  - backlog `registration-note` (19–54 words);
  - a D-entry in `accepted.md`;
  - for parallel runs, again in the tasks.md "Execution model".

  The completion appears in:
  - backlog `completion-note` (29–60 words);
  - verification "Status" or summary;
  - the T-12 evidence field in tasks.md.

  The backlog `acceptance` field ("AC-01 through AC-11 in the specification cover …", 20 items, 1,066 words) only paraphrases the spec's AC list.
- **Evidence:** AIU-055 has `approval_basis` (180 words), registration-note (51), D-204, D-205 and D-206, and the tasks.md Execution model item 1. It also has completion-note (60), the verification "Status" section and the T-12 evidence. D-204 to D-206 restate spec requirements nearly verbatim.
- **Label:** fact.
- **Confidence:** high.
- **Impact:** Quality: copies drift apart (F6, F7). Speed: about 200–350 extra words written per feature, plus edits at numbering time.
- **Proposed direction:**
  - Keep approval provenance in one place: the spec `approval_basis`.
  - Make the backlog a pointer: status plus links.
  - Create a D-entry only for a durable cross-feature rule, not for each feature's chosen UI variant, which belongs in the spec.
  - Write the completion summary once, in verification.md.
- **KEEP:** Owner-approval provenance (`approval_basis`, never fabricated), because the constitution and formats require it. D-entries for durable cross-cutting rules such as D-190 and D-196.

### A2-F3 — tasks.md files are one-shot implementation plans, the largest record, never referenced afterwards
- **Observation:**
  - Recent tasks.md files are superpowers implementation plans: checkbox steps, code-level instructions, worker briefs and global constraints.
  - The tasks.md is the largest file in every recent folder that has one, at 1.4 to 2.8 times the spec:

    | Feature | tasks.md (words) | spec (words) |
    | --- | --- | --- |
    | AIU-055 | 6,155 | 2,175 |
    | AIU-046 | 3,826 | 1,315 |
    | AIU-048 | 3,099 | 1,206 |
    | AIU-053 | 2,540 | 1,128 |
    | AIU-054 | 1,151 | 942 |

  - Across all specs, tasks.md accounts for 5,238 of 22,200 Markdown lines.
  - No tasks.md is referenced by any tracked file outside its own folder: 0 of 28. By comparison, 35 of 38 spec.md and all 37 verification.md files are referenced from outside.
  - After the merge, the code and verification.md supersede the plan.
  - formats.md defines tasks.md as "internal task state and concise handoff, not … an authorization ledger". AIU-055's file is 737 lines and records owner authorizations: "pushes and merges to `main` … are owner-authorized".
- **Evidence:** `work/A2/xref2.txt`. Transcripts show 54 Reads against 85 Write/Edit calls on tasks.md; the reads come from workers during execution, which is real value while the plan runs.
- **Label:** fact (size, references); inference (post-merge value ≈ nil).
- **Confidence:** high.
- **Impact:** Quality: an executed plan pasted into the repository looks binding. If code later diverges, a reader cannot tell. Speed: writing a 3–6k-word plan and then mirroring each task's status into it (F4).
- **Proposed direction:**
  - Treat a plan as an execution artifact.
  - Keep it while the feature runs, or keep it in `.ai-usage-local/` when one agent works alone.
  - At completion, collapse it to a task ledger with one line per task (ID, title, commit(s), evidence) inside verification.md. Alternatively, delete it; git history preserves it.
  - Move reusable parts (worker procedure, desktop-smoke lock, report format), which appear in AIU-055 and similar plans, into one shared workflow doc or agent definition instead of re-pasting them per feature.
- **KEEP:** The T-block contract with acceptance and evidence for active parallel work, because the validator's ownership and overlap checks protect parallel workers. The worker procedure content, moved to one shared place.

### A2-F4 — About 37 % of commits only edit records; per-task "record T-xx" commits are 10 % of recent history
- **Observation:**
  - 154 of 405 non-merge commits (38 %) touch only spec, backlog, goals or decision files. Since 2026-10-05 (Claude Code only) the figure is 57 of 157 (36 %).
  - Subjects matching "record T-" number 19 overall, 16 of them since 2026-10-05 (10 %), mostly AIU-055 T-01 to T-11.
  - The AIU-055 controller procedure requires a separate `docs(AIU-055): record T-0n` commit and push after each worker (tasks.md Execution model, step 3).
- **Evidence:**
  - `git log` path classification;
  - commits 87c34e6, b81ef9e and 22e1324;
  - the workflow triggers on every push to `main` without `paths-ignore`, and the Preview job runs on push to `main` when the repository variable is enabled.
- **Label:** fact (counts, trigger config); inference (each record-only push costs a full CI run and possibly a Preview build; I did not verify whether `promote` skips unchanged builds).
- **Confidence:** high for counts; medium for the CI cost.
- **Impact:** Speed: extra merge-and-push cycles for the controller, merge conflicts on shared records, and CI and Preview churn. Quality: none gained, because tasks.md and verification.md already receive the same facts.
- **Proposed direction:**
  - Record worker evidence in batches, once per wave or once at feature end.
  - Keep the worker's own `feat/fix(...)(T-0n)` commits as the per-task trace.
  - Optionally add `paths-ignore` or a docs-only fast path in CI. That is a cross-lane CI item, and the owner must decide on Preview behaviour.
- **KEEP:** Save-point commits for code (owner Git policy), and per-task commit tags `(T-0n)`, which give real traceability.

### A2-F5 — Verification evidence is valuable but pastes the same commands dozens of times
- **Observation:**
  - Verification AC tables of the form "AC-01 PASS evidence …" are concrete, honest about NOT_RUN and include red-then-green proof. This is the highest-value record.
  - The same 4–8 command lines are pasted into every file: 25 verification or tasks files contain the full Presentation-suite command, and 254 `dotnet …` command occurrences appear across verification and tasks files.
  - AIU-055's "Per-task evidence" table has about 57 rows. Most repeat the suite, build and smoke commands with intermediate pass counts that the integrated T-12 table then supersedes.
  - Transcripts show 134 Write/Edit calls against 34 Reads on verification.md.
- **Evidence:**
  - AIU-055 verification.md, 131 lines with very long rows;
  - the AIU-052 verification.md commands table, compared with README "local checks";
  - `work/A2/reads.py` output.
- **Label:** fact.
- **Confidence:** high.
- **Impact:** Speed: writing and reading bulk. Quality: none; the extra rows hide the decisive rows (red-green tests, review verdicts).
- **Proposed direction:**
  - Name checks by their README or verification.md matrix identifier ("Presentation suite: PASS 330/330 at `87c34e6`") instead of the command, and give a command only when it deviates.
  - Per task, keep one line: commits, red-to-green test, review verdict and residual findings.
  - Keep the integrated final table.
- **KEEP:** The AC → status → evidence table, the NOT_RUN/BLOCKED table with reasons, the review verdict and residual findings, the host/base commit line, and the red-then-green notes. These are what make completion claims checkable.

### A2-F6 — Specs and backlog outcomes go stale when a later decision amends behaviour
- **Observation:** Specs are point-in-time, yet formats.md calls spec.md "accepted intended behavior".
  - AIU-051's spec (AC-02) and its backlog outcome still say that settings "slides in from the right and narrows the cards".
  - D-197 (commit dc7e8fd, the next day) replaced that with a sheet that drops down over the body. Neither AIU-051 file was updated or marked amended.
  - 26 of the 27 decisions from D-180 onward contain amends/supersedes/replaces wording.
  - Only AIU-038's spec shows signs of being kept up to date (D-201 renumbering touched it).
- **Evidence:** `docs/specs/AIU-051-single-column-settings-sheet/spec.md` line 46; backlog AIU-051 outcome; decisions D-193 and D-197.
- **Label:** fact (AIU-051 example); inference (pattern is general; 26/27 is a keyword count).
- **Confidence:** medium-high.
- **Impact:** Quality: an agent reading a feature spec to change that UI gets the wrong current behaviour, which risks regressions or wasted clarification questions. Speed: a reader has to cross-check decisions.
- **Proposed direction:** Choose one model explicitly.

  The validator could check (b) cheaply: a D-entry that says "amends AIU-0xx" must be linked back.

### A2-F7 — Merge-time numbering leaves placeholders and wrong IDs in permanent history and touches code
- **Observation:**
  - Since D-196 (2026-10-08), 27 commit subjects permanently carry `AIU-NEW` (19) or `D-NEW` (8).
  - `git log --grep AIU-053` finds 0 commits, because the feature was built entirely under `AIU-NEW`.
  - Commits e97e843 and e346a4e say D-194 for work that became D-195, after the renumbering that preceded D-196.
  - Renumbering is its own commit or step and touches backlog, goals scope, decisions, spec, tasks (44 lines in 22e1324), verification and source comments (4 `src` files in 902b196, 2 in d8b5efa).
  - Numbering-only commits since 2026-10-05: 7 (10477c3, d8b5efa, 65f7fcb, b81ef9e, 22e1324, plus mixed 902b196 and 8bac814).
  - AIU-054's verification still names the evidence folder `.ai-usage-local/AIU-NEW/`.
  - The procedure needs fetch, merge, replace everywhere, run `--final`, commit and push, and repeat on rejection.
- **Evidence:** the commits above; CONTRIBUTING Git policy; ProjectValidator.cs lines 18–20 and 59–62.
- **Label:** fact.
- **Confidence:** high.
- **Impact:** Quality: traceability by ID breaks in `git log` and `blame`, though path-based `git log --follow` still works. Speed: an extra rewrite pass per feature, with source edits for D-IDs in comments. A rejected push repeats the whole pass.
- **Proposed direction:** This is an owner decision (D-196 chose placeholders over provisional numbers). Options:
  - (a) Reserve the number at creation by pushing a one-line backlog stub or decision heading to `main` immediately, which fits the push-to-main policy and needs no rewriting.

  - (c) Stop referencing D-IDs in source comments: 74 D-references and 89 AIU-references in .cs files.
- **KEEP:** The `--final` CI gate, which guarantees `main` never holds a placeholder. Stable numeric IDs on `main`.

### A2-F8 — The validator polices execution plumbing but not evidence substance or decision IDs
- **Observation:**
  - Enforced: required metadata, statuses, the dependency graph, goal↔backlog scope, spec↔backlog status pairing, the AC-NN format, existence of done evidence, parallel ownership (`writes` overlap, PRIMARY_SHARED, WORKER_ISOLATION, DONE_WITHOUT_INTEGRATION), safe paths, links, skills and placeholders.
  - Not enforced:
    - duplicate or colliding `D-NNN` decision IDs, which is the very collision D-196 addresses;
    - that verification.md reports every spec AC;
    - that a done item's NOT_RUN owner checks are listed anywhere;
    - spec `type`, which is free text.
  - Retired-tool residue: the scan includes `.omp/AGENTS.md` and `.github/copilot-instructions.md`, and `PrimaryPath` lists `.omp/`.
  - "Done requires evidence" is satisfied by the existence of verification.md, not by its content.
- **Evidence:** ProjectValidator.cs lines 47, 65–147, 224–228; test codes in ValidatorTests.cs.
- **Label:** fact.
- **Confidence:** high.
- **Impact:** Quality: the cheapest high-value checks (D-ID uniqueness, AC coverage) are missing, while ceremony checks force fields such as a `trigger` on every item. Speed: neutral.
- **Proposed direction:**
  - Add D-ID uniqueness and an AC-coverage check: every `AC-NN` of a done spec appears in verification.md, or a stated range covers it.
  - Drop `.omp` paths after the lane-A1 cleanup.
  - Revisit whether `trigger` and `scope_version` earn their place. `scope_version` is 1 in 30 of 38 specs.
- **KEEP:** Dependency, link, safe-path, placeholder and done-without-evidence checks, plus parallel-ownership checks while parallel workers are used (AIU-055 ran 11 of them).

These sit in 24 NOT_RUN mentions in backlog.md and 7 or more verification files. Nothing lists what the owner should check after an update, and nothing records when a check happened.
- **Evidence:** `grep NOT_RUN docs/backlog.md` gives 24; `grep -l D-190 docs/specs/*/verification.md` gives 7.
- **Label:** fact (counts); inference (risk).
- **Confidence:** high.
- **Impact:** Quality and owner control: live-account behaviour (Copilot Business, Claude spending, tray) may never be confirmed, and NOT_RUN quietly becomes permanent. Speed: the owner or an agent must hunt across files.
- **Proposed direction:** One short "Pending owner checks" list (a backlog section, or a single file), with one line per check: feature, what to look at, added date. An agent appends to it at completion and removes the line when the owner confirms. This replaces the per-item NOT_RUN prose in the backlog.

## Proposed lean record system (proposal only)

1. **backlog.md:**
   - Live items in full, with fields `goal`, `status`, `depends_on`, `outcome` and an optional `note`.
   - A "Done" index table with one row per item: ID, title, goal, date, spec and evidence links.
   - A "Pending owner checks" list (F9).
2. **Feature folder:**
   - `spec.md`: frontmatter with the single approval provenance and an `amended_by` list; Problem, R-xx, AC-xx, Out of scope.
   - `verification.md`: an AC table, checks named by their matrix ID, Not run, Review, and a task ledger with one line per task when tasks existed.
   - `design.md` only when architecture is at stake.
   - The plan is ephemeral, or collapsed into the ledger at completion.
3. **Light change:** one `record.md` holding problem, chosen variant, ACs and evidence, plus a backlog index line. No D-entry unless the change sets a cross-feature rule.
4. **Status lives once** in the backlog; the spec lifecycle is derived or reduced to draft/approved/implemented.
5. **Evidence is recorded in batches** at wave or feature end; there are no per-task record commits.
6. **Validator:** add D-ID uniqueness and AC coverage; drop the `.omp` paths.

**Estimated savings (inference):**
- **Backlog:** about 11k → about 3.5k words (−65 to −70 %), roughly 10k fewer tokens per full read.
- **Record words per parallel feature:** −40 to −55 %. For AIU-055, about 11k → about 5k words: the tasks plan is gone, the per-task table becomes 11 lines, and the notes are not mirrored.
- **Small changes:** −40 % record words.
- **Commits:** record-only commits drop from about 36 % to an estimated 15–20 %, which is roughly 10–15 fewer pushes and CI runs a week at the current pace.
- **Numbering:** no source edits for IDs, and with option (a) of F7 no rewrite pass at all.
- **Unchanged:** traceability (IDs, links, commit tags), ACs and verification evidence.

## KEEP

- **Spec AC-NN and R-xx with testable conditions:** they are the acceptance contract, reused by later specs.
- **The verification AC → status → evidence table, explicit NOT_RUN/BLOCKED with reasons, review verdicts and red-then-green proof:** they make completion claims checkable.
- **Approval provenance, recorded once and never fabricated:** it is an owner-control requirement.
- **The validator's link, dependency, safe-path, done-without-evidence and `--final` placeholder checks, and its parallel-ownership checks while parallel workers are used:** these are cheap automated guards.
- **D-entries for durable cross-feature rules (for example D-190 and D-196):** they carry real policy.
- **Per-task `(T-0n)` tags in code commit subjects:** they are the real execution trace.
- **Honest separation of PASS, FAIL, NOT_RUN and BLOCKED:** AGENTS.md requires it.
