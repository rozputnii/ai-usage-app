## Findings

### B6-F1 — The current test baseline already resists most AI-test failure modes
- **Observation:** Owned-code warnings are errors (`TreatWarningsAsErrors`, `AnalysisMode=Recommended`, `EnforceCodeStyleInBuild` in `Directory.Build.props`, which applies to tests too). Tests assert concrete independent values (for example `ParserLedgerTests` checks 12.50m, 500, reset 2026-11-01) rather than re-deriving them from production code. Boundary tests exist (`DependencyBoundaryTests`, `ProviderBoundaryTests`). View models are tested without WinUI by compile-linking `Features/**/*.cs` into `AiUsage.Presentation.Tests`, which is close to Microsoft's "move logic out of the app project" advice. The golden-fixture policy in `verification.md` forbids blanket snapshot approval and requires independent critical assertions. `aiu-implementer` must show the failing test before implementing. Desktop smoke fails with `BLOCKED:` rather than silently skipping (`DesktopTestEnvironment.RequireUnlockedDesktop`). There are no `Skip =` tests; 4 files use `Explicit = true` for Sandbox/guest scenarios. About 711 `[Fact]`/`[Theory]` methods and about 3,900 `Assert.` calls in `tests/windows`.
- **Evidence:** files above; grep counts.
- **Label:** OBS. **Confidence:** High.
- **Impact:** Quality high (already realized). Speed neutral.
- **Proposed direction:** Keep it. Add only the small, mechanical checks in F2/F3 where agents can still slip.
- **Verdict:** Keep.
- **Security/supply-chain:** One test dependency (xunit.v3) plus FlaUI. Minimal.
- **Effort and upkeep:** None.
- **KEEP:** All of the items above, especially the linked-source VM testing and the "never blanket approve fixtures" rule.

### B6-F2 — Test-erosion sentinel: make deleted, skipped and weakened tests visible mechanically
- **Observation:** The risks that remain for AI-written changes are silent ones: deleting or skipping tests, converting `[Fact]` to `Explicit`, cutting `Assert` calls, or editing fixture expected outputs in the same commit as parser changes. History shows that large legitimate deletions do happen (`542598e` removed 20 presentation test files when the old UI was retired; `44ae02e` removed 2 history test files). Today nothing flags these apart from a human reading the diff.
- **Evidence:** `git log --diff-filter=D -- tests/**/*.cs`; `verification.md` "Golden fixtures"; xUnit1004 ("Test methods should not be skipped") is an Info-level analyzer by default (INF from memory; the rule page does not state severity), so it does not trip warnings-as-errors.
- **Label:** OBS + INF. **Confidence:** Medium-high.
- **Impact:** Quality medium-high, because it catches the most common AI-test regression cheaply. Speed: a few seconds.
- **Proposed direction:** Add one small script (PowerShell, or a `--test-diff` mode in the existing `tools/AiUsage.ProjectValidation`) that compares `HEAD` (or the working tree) with the merge base. It should report: test files deleted; net change in `[Fact]`/`[Theory]`/`[InlineData]` counts; new `Skip`, `SkipWhen`, `SkipUnless` or `Explicit` occurrences; net `Assert.` decrease per file; and changes to `tests/**/Fixtures/*` or expected JSON. It should be advisory: print the findings and require one justification line in the commit body or verification record (for example "Tests-removed: retired old UI, AIU-039"). The reviewer agent reads this output. Also set `dotnet_diagnostic.xUnit1004.severity = error` in `.editorconfig`, which costs nothing because no Skip exists today.
- **Verdict:** Adapt idea (homegrown script, no dependency).
- **Security/supply-chain:** None. Local git only.
- **Effort and upkeep:** About 2–3 hours. Low upkeep because it only uses regex on the diff.
- **KEEP:** Keep it advisory. Do not block on a count drop, because legitimate retirements exist.

### B6-F3 — Make red-green evidence checkable ("fails without the fix")
- **Observation:** `aiu-implementer` must show the red run, but the evidence is the implementer's own report. `aiu-reviewer` re-runs acceptance commands on the final code. Nobody re-proves that the new test fails on the old code, and that is the property that defeats tests which mirror the implementation or are vacuous.
- **Evidence:** `.claude/agents/aiu-implementer.md` and `aiu-reviewer.md`.
- **Label:** OBS + INF. **Confidence:** High.
- **Impact:** Quality high for bug fixes and behavior changes. Speed: one extra targeted run, measured in minutes.
- **Proposed direction:** For bug fixes and material behavior changes only, the reviewer creates a temporary `git worktree` at the base commit, copies in only the changed and added test files, runs the targeted classes (`-class`/`-method`, see F7), and expects failure. It then confirms that the same tests pass on HEAD. If the changed tests do not compile against the base, a compile failure counts as red; the reviewer notes it and does not dig further. Add 3–4 lines to `aiu-reviewer.md` and a one-line rule to CONTRIBUTING/verification. Skip this for pure refactors, documentation, and new features where everything is new.
- **Verdict:** Adopt (process note, no tooling).
- **Security/supply-chain:** None. Use `git worktree`, never a bare `git stash` (shared stash stack).
- **Effort and upkeep:** About 30 minutes to write. Each use costs one targeted test run.
- **KEEP:** Implementer-side TDD stays. This is the independent counterpart to it.

### B6-F4 — Mutation testing (Stryker.NET 5.0): on-demand trial on pure logic, not a gate
- **Observation:** Mutation score is the only automated measure of assertion strength, so it targets "tests that execute code but don't check it". dotnet-stryker 5.0.0 (2026-09-11) targets the .NET 10 runtime. However, xUnit v3 needs Stryker's MTP runner (`--test-runner mtp`), which the 2026-03-13 blog called preview. 5.0 added `perTest` coverage for MTP, but its notes do not say whether the runner is still preview. A third-party ADR (Needlr) reports that the VSTest runner does not reliably apply mutants to xUnit v3, and that the MTP runner ignored filters and was slow on a large project. The repo's test projects run through xUnit's native runner (`dotnet run`), and MTP is not enabled.
- **Evidence:** Stryker releases and blog; Needlr ADR-0011/0012; test `.csproj` files have no `UseMicrosoftTestingPlatformRunner`.
- **Label:** EXT + INF. **Confidence:** Medium. Compatibility with this repo's xunit.v3 3.2.2 setup is unverified.
- **Impact:** Quality medium-high for Core and parser math (`BudgetEngine`, `LimitModel`, `ReorderMath`, quota parsers). Speed negative per run (minutes to tens of minutes), so keep it out of the inner loop.
- **Proposed direction:** Run a time-boxed spike (half a day or less) on one project: Core plus `AiUsage.Infrastructure.Tests`, `mutate` limited to `Budget/**` and the parsers. Pin `dotnet-stryker` in `.config/dotnet-tools.json`. If it works, an agent runs it on demand when a change touches pure calculation code and treats surviving mutants as review input, not a gate. If the spike needs MTP enablement or produces noisy results, drop it and rely on F2/F3.
- **Verdict:** Trial (spike with a kill criterion).
- **Security/supply-chain:** A NuGet .NET tool that runs and rewrites builds locally. Pin the exact version and do not add it to CI. Active project (multiple 2026 releases).
- **Effort and upkeep:** Spike half a day. Upkeep: version bumps and config only.
- **KEEP:** Do not adopt a mutation-score threshold. Thresholds can be gamed and create churn.

### B6-F5 — Property-based testing: CsCheck for 2–3 invariants
- **Observation:** Pure arithmetic and ordering code (budget pacing, money quantities with exponents, reorder math, reset calendars) is example-tested. Property tests find edge cases that agents don't think to enumerate: rounding, boundary dates, empty/one-element orders, and parsers that must never throw on arbitrary JSON.
- **Evidence:** Test names `ReorderMathTests`, `MonetaryUsageTests`, `BudgetEngineTests`, `*ParserTests`; CsCheck 4.9.1 (2026-09-17), zero dependencies, Apache-2.0, works inside plain xUnit `[Fact]`s. FsCheck 3.4.0 pulls FSharp.Core.
- **Label:** EXT + INF. **Confidence:** Medium.
- **Impact:** Quality medium (targeted). Speed: runs in milliseconds to seconds.
- **Proposed direction:** When a change next touches one of these areas, add CsCheck to `Directory.Packages.props` (test projects only). Write a few properties: reorder is a permutation that preserves the ids; money add/subtract round-trips at a fixed exponent; parsers return `false` without throwing on fuzzed bytes or JSON. Use a fixed seed in CI for reproducibility, and print the seed on failure.
- **Verdict:** Trial (CsCheck); reject FsCheck because it brings an F# runtime dependency for no added benefit here.
- **Security/supply-chain:** Single package, no transitive dependencies, test-only.
- **Effort and upkeep:** 1–2 hours for the first properties. Low upkeep.
- **KEEP:** Example tests with concrete expected values remain primary.

### B6-F6 — Snapshot/approval testing (Verify): reject
- **Observation:** Verify is excellent and very active (Verify.XunitV3 33.3.2 released today, 6 dependencies including DiffEngine). Its workflow, though, is "accept the `.received` file", which is exactly the rubber-stamp move that `verification.md` forbids ("never blanket approve snapshots to get green"). An agent can accept a wrong snapshot as easily as a right one. The repo's golden fixtures already use sanitized input and independent critical assertions.
- **Evidence:** NuGet; `verification.md` Golden fixtures.
- **Label:** EXT + OBS. **Confidence:** High.
- **Impact:** Quality negative risk for AI workflows. Speed: slight gain in authoring.
- **Proposed direction:** None. F2 already flags expected-fixture edits.
- **Verdict:** Reject.
- **Security/supply-chain:** 6 transitive packages, plus a DiffEngine that launches diff tools.
- **Effort and upkeep:** n/a.
- **KEEP:** Current fixture policy.

### B6-F7 — Fast local loop: keep the native xUnit runner, add targeted filtering and build-once
- **Observation:** Tests run as xUnit v3 executables through `dotnet run --project ... -c Release --no-restore`. This is simple and uses the in-process native runner. Each `dotnet run` triggers an incremental build. The local app debug build is `Debug` while the suites are `Release`, so Core and Infrastructure are compiled in both configurations. No `[Trait]` is used anywhere, so the inner loop can only narrow by class or method. .NET 10's MTP mode for `dotnet test` (opt-in via `global.json` `"test": {"runner": "Microsoft.Testing.Platform"}`) offers solution-level parallel runs, `--minimum-expected-tests` (exit code 9), trx and coverage extensions, and xUnit filters such as `--filter-class` and `--filter-trait`. MSBuild Server is off by default in .NET 10 (`DOTNET_CLI_USE_MSBUILD_SERVER=1`) and becomes the default in .NET 11.
- **Evidence:** README "Local checks"; test `.csproj` files; MS Learn `dotnet-test`, `msbuild-server`; xUnit query-filter docs (`-filter "/[area=budget]"`, `-class`, `-method` in native mode).
- **Label:** OBS + EXT. **Confidence:** Medium-high. Actual timings come from lane A6.
- **Impact:** Speed medium for agent inner loops. Quality neutral.
- **Proposed direction:** (a) Document an inner-loop form in README, for example `dotnet run --project tests/windows/AiUsage.Infrastructure.Tests -c Release --no-restore -- -class "*Budget*"`, with full suites still required before commit. (b) For the completion run, use `dotnet build` once for both test projects, then `dotnet run --no-build` for each, which avoids a duplicate up-to-date check. (c) Trial `DOTNET_CLI_USE_MSBUILD_SERVER=1` in agent sessions. Benefit should show when many builds run in close succession, but watch for file locks across worktrees. (d) Defer the MTP migration: it adds `global.json` and project changes for features not needed now. Revisit only if the Stryker spike (F4) requires MTP. (e) Add `[Trait("area", …)]` only if A6 shows full-suite time is material. Class filters cover most needs without touching 700 tests.
- **Verdict:** Adopt (a, b); trial (c); defer (d, e). Reject `dotnet watch test` for agents (agents run discrete commands) and test-impact-analysis tooling (no mature free .NET option, and the suites are small).
- **Security/supply-chain:** None.
- **Effort and upkeep:** Under 1 hour, documentation only.
- **KEEP:** `dotnet run` native runner, `--no-restore` with BLOCKED on missing assets.

### B6-F8 — CI speed: NuGet caching only if A6 shows restore is material; lock files have a security upside
- **Observation:** `validate` and `windows-package` restore from scratch on `windows-latest` (WindowsAppSDK and SDK BuildTools are large). `actions/setup-dotnet`'s `cache: true` needs `packages.lock.json`, and none exist. Lock files also record content hashes, which adds supply-chain integrity (EXT/INF). Learn recommends pinning the SDK exactly (`rollForward: disable`) with lock files, while the repo uses `latestPatch`.
- **Evidence:** `validation.yml`; MS Learn NuGet caching page.
- **Label:** OBS + EXT. **Confidence:** Medium.
- **Impact:** Speed low-medium (tens of seconds to minutes per job; unmeasured). Quality: small integrity gain.
- **Proposed direction:** Decide after A6 measures restore time per job. If it is over about 60 s, enable `RestorePackagesWithLockFile` centrally, add `cache: true` and `cache-dependency-path: '**/packages.lock.json'`, and use `--locked-mode` in CI.
- **Verdict:** Trial (conditional).
- **Security/supply-chain:** Positive (hash-pinned restore); `actions/setup-dotnet` is already SHA-pinned.
- **Effort and upkeep:** 1 hour. Lock files churn with each package bump (bots/agents regenerate them).
- **KEEP:** SHA-pinned actions, `persist-credentials: false`, separation of the package job.

### B6-F9 — WinUI UI test tooling: keep FlaUI UIA3; reject Appium/WinAppDriver and a second framework
- **Observation:** FlaUI 5.0.0 (Feb 2025, newest target .NET 8, runs on .NET 10 through compatibility; 243 open issues) is maintained slowly but adequately for a thin UIA wrapper. Microsoft's WinUI testing page says WinAppDriver is "no longer under active development" and recommends Appium with appium-windows-driver, which needs Node.js and an Appium server and, per WebdriverIO, still proxies WinAppDriver. Microsoft also documents MSTest `[UITestMethod]` WinUI test apps on MTP, including unpackaged ones (MSTest.Sdk 4.5+). That would add a second test framework and a WinUI host project.
- **Evidence:** FlaUI releases; Learn windows/apps/develop/testing; Learn unit-testing-mstest-winui; webdriver.io Windows docs.
- **Label:** EXT. **Confidence:** High for Appium/WinAppDriver; medium for FlaUI longevity.
- **Impact:** Quality neutral (no regression). Speed: avoids migration cost.
- **Proposed direction:** Keep FlaUI for critical launch/tray/activation smoke. Keep VM and logic tests as the main UI-behavior net. Revisit `[UITestMethod]` only if XAML-level regressions such as converters, templates or bindings become a recurring defect class that VM tests miss. Watch FlaUI for a .NET 10-era release; if it goes dormant, the fallback is direct `UIAutomationClient` COM interop, not Appium.
- **Verdict:** Keep FlaUI; reject Appium/WinAppDriver; reject MSTest WinUI for now.
- **Security/supply-chain:** FlaUI has a small surface. Appium would add an npm toolchain and a local WebDriver server.
- **Effort and upkeep:** None.
- **KEEP:** `DesktopTestEnvironment` BLOCKED guards, `Explicit` for guest-only scenarios, evidence screenshots.

### B6-F10 — Smoke reliability: AutomationId-first locators and one polling helper
- **Observation:** Since 2026-09-20, 74 commits have touched `tests/windows/AiUsage.Windows.Tests`. Several are pure locator or timing repairs: "resolve the Ledger window afresh", "invoke buttons only once they are enabled", "finds the tray overflow chevron by id and prefix". The suite uses `ByName(` 71 times against `ByAutomationId` 22 times, and has 25 `Thread.Sleep` calls in about 3,600 lines. XAML declares only 2 explicit `AutomationProperties.AutomationId` (WinUI falls back to `x:Name`, INF). Name locators couple smoke to UI copy, which changes often under the variant-first UI process.
- **Evidence:** git log grep; locator counts.
- **Label:** OBS + INF. **Confidence:** Medium-high.
- **Impact:** Speed high, because fewer agent cycles go to fixing smoke after copy or layout changes. Quality medium, because there are fewer false failures.
- **Proposed direction:** (1) Add one helper set in `AiUsage.Windows.Tests`: `WaitFor(locator, condition, timeout)` that re-resolves from the window each poll and checks `IsEnabled`/`IsOffscreen`; `InvokeWhenReady`. Replace `Thread.Sleep` with these except where a documented OS settle delay is needed. (2) Prefer `x:Name` or `AutomationId` for controls the smoke drives. Adding an AutomationId is not a visible UI change, so no design variants are needed. (3) On any assertion failure, automatically capture a screenshot and a bounded UIA subtree dump into the evidence directory, which saves a rerun when diagnosing. Do this incrementally as each smoke file is next touched, not as a big-bang rewrite.
- **Verdict:** Adapt idea.
- **Security/supply-chain:** None. Keep UIA dumps free of provider data: demo or empty state only, which is already the default smoke mode.
- **Effort and upkeep:** Helper about 2 hours; migration is incremental.
- **KEEP manual:** Visual or aesthetic judgment of layout, tray icon appearance in the real taskbar of the installed app, live-provider flows (post-deploy owner checks, D-190), and package install/update outside Sandbox.

### B6-F11 — Agent self-verification guardrails: one fast hook, no coverage gates
- **Observation:** No Claude Code hooks are configured (`.claude/settings.local.json` only allows a skill). Stop and SubagentStop hooks can block with exit 2 and feed stderr back. `asyncRewake` hooks can run in the background and wake the agent on failure. Coverage-delta gates reward tests that execute code without asserting, the opposite of what AI-written tests need.
- **Evidence:** Claude Code hooks reference; repo settings.
- **Label:** OBS + EXT + INF. **Confidence:** Medium.
- **Impact:** Quality medium, because agents can't "finish" with an unflagged erosion or whitespace error. Speed: hook under 10 s.
- **Proposed direction:** Add a project `SubagentStop` hook (matcher `aiu-implementer`) and optionally a `Stop` hook that runs only fast deterministic checks: `git diff --check` and the F2 sentinel. It blocks only when the sentinel reports unjustified erosion. Do not run the full suites in the hook, because that is slow and can loop on Stop. Suites stay explicit commands in the verification matrix. As an optional cheap floor in CI, parse the xUnit summary ("Total: N") and fail if a suite reports 0 tests. MTP's `--minimum-expected-tests` would do this natively if MTP is ever adopted.
- **Verdict:** Adapt idea (hook plus sentinel); reject coverage-percentage or coverage-delta gates.
- **Security/supply-chain:** The hook runs a repo script; review it like code. This is a settings change, so it needs owner approval (AGENTS: no agent-authorized config change).
- **Effort and upkeep:** 1 hour on top of F2.
- **KEEP:** Honest PASS/FAIL/NOT_RUN/BLOCKED reporting; CI `validate` as the authoritative gate before Preview publication.

## Open questions for the owner

1. **Erosion sentinel strictness (F2/F11):** should unjustified test removals only warn, or block the implementer subagent's stop (exit 2) until a justification line exists? My recommendation is to block only the subagent and only warn the primary.
2. **Stryker spike (F4):** may an agent spend about half a day trialing mutation testing on Core budget math and parsers, with "drop if it needs MTP migration or is noisy" as the kill criterion? This adds a pinned local .NET tool.
3. **CsCheck (F5):** is one new test-only package with zero dependencies acceptable the next time budget or reorder code changes?
4. **Hooks (F11):** a project-level hook changes Claude Code configuration. Do you want it in `.claude/settings.json` (shared, versioned) or not at all?
5. **Smoke locators (F10):** may agents add `x:Name`/`AutomationId` to XAML controls the smoke drives, treating this as a non-visual change that needs no design variants?
