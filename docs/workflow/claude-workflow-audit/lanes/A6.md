## Findings

### A6-F1 — Infrastructure suite wall time comes from two serial test classes
- **Observation:** The suite's 24.4 s wall time is set by two classes. xUnit parallelizes by class, so a large class runs serially. `AuditScenarioTests` takes 22.7 s: its single theory `ParserRecorderBudgetAndProjectionMatchIndependentExpectations` has 235 cases that each create a real `LocalBudgetStore` in %TEMP%. `LocalBudgetStoreTests` takes 15.8 s, and 14.9 s of that is one test, `ExcessSeriesCannotGrowTheOwnedStoreIndefinitely`, which writes 256 series files. The summed test time is 97.4 s; every other class finishes in 5 s or less.
- **Evidence:** `work/A6/infra.xml`; `tests/windows/AiUsage.Infrastructure.Tests/AuditScenarioTests.cs:285-300`; `LocalBudgetStoreTests.cs:154-160`.
- **Label:** fact (timings); inference (achievable speedup).
- **Confidence:** high.
- **Impact:** Quality: none if done right. Speed: the Infrastructure suite runs at least twice per task (AIU-055 recorded it about 15 times), and could drop from ~25 s to ~8–10 s.
- **Proposed direction:** Split the corpus theory across several classes, or shard the cases by ID prefix, so it runs in parallel. Make the 256-file cap test cheaper without losing the boundary, for example with a smaller injectable cap or a single shared store. Profile first.
- **KEEP:** the 235-case independent-expectation corpus and the store-growth cap assertion.

### A6-F2 — `DiagnosticCrashTests.ForcedKill…` is timing-sensitive on a cold host
- **Observation:** The first `--no-build` run after a cold build failed at `DiagnosticCrashTests.cs:66` (`Assert.True(Directory.Exists(folder))`): the freshly built `AiUsage.DiagnosticsProbe.exe` did not create its log folder within the 10 s poll. The two later runs passed. A previous fix (`13814e1`, 2026-10-06) already addressed a different race in this test. Memory notes record "Defender first-run latency" on this host.
- **Evidence:** `work/A6/timings.log.infra_run_nobuild.out`; `git log -- DiagnosticCrashTests.cs`.
- **Label:** fact (failure); inference (cause: first launch of a new exe).
- **Confidence:** medium.
- **Impact:** Quality: false red in fresh worktrees, which invites "rerun until green" habits. Speed: one rerun of about 30 s plus diagnosis.
- **Proposed direction:** Have the probe signal readiness explicitly (a stdout line) and wait on that with a generous bound (≥30 s), rather than polling the filesystem for 10 s.
- **KEEP:** the forced-kill/no-invented-critical contract.

### A6-F3 — Smoke instability comes mostly from the environment and the harness, not the product
- **Observation:** Aggregated local evidence (414 UI results since 2026-10-01) shows: the launch smoke ran 89 times with 79 pass and 10 fail (median 8.5 s); `AccountSpending…` 73 runs, 68 pass; `MockAuthenticationCodeCancellation…` 59 runs, 33 pass; `NativeTrayClicksRestoreRefreshAndDrainExit` 44 runs, 19 pass; `ReplayPagesRenderUsedAndLeft` 15 runs, 5 pass (median 149 s); `SettingsEditorsHistory…` 11 runs, 4 pass. Recorded failure causes include:
  - the locked desktop (AIU-045 lane BLOCKED for an hour);
  - the owner's installed app's tray icon preceding the test app's icon in the overflow (AIU-055 T-09/T-10, `918b1cd`, `4f2b8a1`);
  - stale UIA element references and wrong target selection (`02e0ca8`, `4c32153`, `11645ac`, `e40c76d`, AUD-03).

  The harness had 86 commits in 30 days. AIU-055 still lists a known limit: the smoke can invoke the installed app's tray icon.
- **Evidence:** the `.ai-usage-local/**/*.xml` aggregation; `docs/specs/AIU-055-…/verification.md` (T-09, T-10 rows, "Known limits"); `docs/specs/AIU-045-…/verification.md:109-124`.
- **Label:** fact (counts and recorded causes); inference (that most failures are non-product; the counts also include red-first runs).
- **Confidence:** medium.
- **Impact:** Quality: tray assertions can touch the owner's real app, and a flaky smoke erodes trust in red. Speed: the largest repeated cost in UI tasks (lock waits of up to 30 min, harness fix commits).
- **Proposed direction:** Make the tray lookup identify the test instance unambiguously, for example with a per-run unique tray tooltip passed by the smoke environment, so it never touches the installed app. Track per-test pass/fail history in one ignored CSV so flakiness is visible. Retire or rewrite the chronic failures (`ReplayPages…`, `NativeTrayClicks…`) only after the owner decides whether they are still needed (see F9).
- **KEEP:** `LedgerLaunchSettingsHistoryAndExit` as the Preview gate, `DesktopTestEnvironment` fail-closed BLOCKED checks, and red-first smokes for UI behavior.

### A6-F4 — Smoke is the only defence for a third of the Windows code and it does catch real regressions
- **Observation:** Of the 45 fix commits since 2026-09-20 that touched `src/`, 31 changed unit tests, 5 changed only smoke and 9 changed neither. The non-unit fixes sit in code-behind, Controls and lifetime code that no unit project compiles. Examples:
  - `c8804cd`: "restore launch, tray actions" (tray menu Click handlers replaced by commands; fixed together with the new 225-line `LedgerActivationSmoke`);
  - `33760d4`: tray icon unresponsive after a background relaunch (no test added);
  - `e5013fa`: blank tray icon above 100% scale (no test);
  - `4a03028`: tab stops and focus frame (smoke);
  - `6b44650`, `1d45701`: visual tweaks (no test).
- **Evidence:** the commit-to-test mapping script output in this lane; the untested-lines table above.
- **Label:** fact (mapping); inference ("a test should have caught": tray relaunch and the launch regression were catchable by an activation smoke, while colour and visual tweaks need no automated test).
- **Confidence:** medium-high.
- **Impact:** Quality: lifetime and tray regressions reached `main`/Preview and were found by the owner or later work. Speed: post-deploy rework.
- **Proposed direction:** Keep smoke focused on lifetime-critical paths: launch, tray open/refresh/exit, relaunch to the existing instance, close-to-tray. `RepeatedSyntheticLaunchRestoresTheExistingWindow…` exists but ran only twice; consider adding it to the Preview gate set if it proves stable. Do not chase visual tweaks with automation.
- **KEEP:** the launch smoke gate, LedgerActivationSmoke, and the rule that compilation alone is insufficient for UI changes.

### A6-F5 — The Preview gate wording and actual practice disagree, so every pass runs two app builds
- **Observation:** `verification.md` says the gate is "`--demo` startup smoke of the **Release** candidate", and the matrix requires a "package build" for Windows UI changes. In practice the AIU-055 task briefs require a Release build (for the 0-warning check) **and** a Debug build that the smoke targets. AIU-055 T-12 says smokes ran "against the Debug demo build", and AIU-052 records the package build "NOT_RUN locally; CI builds the unsigned package". A no-op WinUI build costs 18–19 s (XAML `MarkupCompilePass2` 10.8 s and `Pass1` 3.2 s run every time); a cold build costs about 30 s.
- **Evidence:** `docs/workflow/verification.md` (Preview gate; matrix row 4); `docs/specs/AIU-055-…/tasks.md:142-155`; AIU-055 and AIU-052 verification records; the MSBuild performance summary in this lane.
- **Label:** fact.
- **Confidence:** high.
- **Impact:** Quality: the gate as written (Release) is not what runs (Debug). Speed: about 20–30 s per pass, repeated before and after each merge per task.
- **Proposed direction:** Choose one configuration. Running the smoke against the Release unpackaged build makes one build serve both the warning check and the gate and matches the gate text. State in the matrix that the "package build" requirement is met by the CI `windows-package` job unless the change touches the manifest or packaging.
- **KEEP:** the warnings-as-errors build check and CI package build.

## KEEP — with reasons

- **The Infrastructure suite (915 cases), including the 235-case audit corpus:** parsers, auth, migration and DPAPI storage are where data loss and credential bugs would occur; 31 of 45 recent src fixes changed tests here or in Presentation.
- **The Presentation suite (330 cases, 1.7 s):** fast, broad view-model coverage made possible by linked compilation.
- **Validator, its tests and `--final`:** cheap (3–4 s) and it caught real defects (`8f05989`, ignored-root links).
- **The launch smoke as the Preview gate, LedgerActivationSmoke, and red-first smokes:** they caught the launch/tray regression (`c8804cd`) and the T-01/T-04/T-09/T-11 behaviors that unit tests cannot reach (3,488 untested lines).
- **`DesktopTestEnvironment` fail-closed BLOCKED checks:** they prevent false PASS on a locked desktop.
- **Boundary/style source scans and the token contrast check:** they enforce owner rules in milliseconds.
- **Warnings-as-errors builds and the CI unsigned package build:** they catch packaging breaks before a Preview is published.
- **Sandbox package/upgrade/feed smokes for packaging, migration and update changes only:** they are the only evidence for install/update and are correctly opt-in.
- **The PASS/FAIL/NOT_RUN/BLOCKED discipline and the D-190 post-deploy NOT_RUN for owner/live checks.**
