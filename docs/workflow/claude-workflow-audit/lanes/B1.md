## Findings

### B1-F1 — The repository's skills in `.agents/skills` are not discovered by Claude Code
- **Observation.** The docs list where skills are found: enterprise, `~/.claude/skills`,
  project `.claude/skills` (including nested and parent directories), `--add-dir`, plugins and
  claude.ai sync. `.agents/skills` is not among them. The repo keeps its three skills
  (`provider-evidence`, `security-lifecycle`, `convergence-review`) only in `.agents/skills`, and
  `AGENTS.md` "Read by task" tells the agent to "use the provider-evidence skill" and similar.
  None of the three appears in this session's available-skills list, while bundled, plugin and
  synced skills do. So the Skill tool cannot invoke them. Claude sees them only if it decides to
  open the file by path, which `AGENTS.md` never gives.
- **Evidence.** Skills doc, "where skills live" table (2026-10-08). `.agents/skills/*/SKILL.md`.
  `AGENTS.md` lines in "Read by task". `docs/workflow/formats.md:50` (the validator reads
  `.agents/skills`). `docs/workflow/agent-neutral-migration-verification.md:45` ("Native
  discovery is optional", a Codex/OMP-era decision). Codex has been disabled since 2026-10-05
  (memory `claude-code-only.md`).
- **Label.** Fact for the discovery paths and the missing listing. Inference that
  security-sensitive guidance is therefore often skipped.
- **Confidence.** High.
- **Impact.** Quality: high. The provider-evidence and security-lifecycle guardrails are the
  repo's security boundary guidance. Speed: neutral.
- **Proposed direction.** Move the skills with `git mv .agents/skills .claude/skills`. Point the
  validator's skill root (`CheckSkills`) and `formats.md:50` at `.claude/skills`. Change the
  `AGENTS.md` "Read by task" lines to name the skills. `.git/info/exclude` excludes only
  `.claude/agents/` and `.claude/worktrees/`, so `.claude/skills` would be tracked. Worktrees get
  it through checkout. Fallback with no code change: put explicit paths in `AGENTS.md`
  (`.agents/skills/<name>/SKILL.md`). Do not use directory symlinks: they need Developer Mode or
  `core.symlinks` on Windows, and they are fragile.
- **Verdict.** **Adopt** the move. It is a small code change with a large reliability gain.
- **Security/supply-chain.** None new. The content is unchanged.
- **Effort and upkeep.** About 1 hour including validator tests. No ongoing upkeep.
- **KEEP.** Keep the skill text and the spec-compatible frontmatter (`name`, `description`).

### B1-F2 — Sessions run in `bypassPermissions` on the bare host; owner safety rules are prose-only
- **Observation.** The docs recommend bypass mode only for isolated containers or VMs. In bypass
  mode, only deny rules, PreToolUse hooks and a few hard-coded checks still hold; allow rules
  have no effect. The OS sandbox is not available on native Windows (WSL2 only). Auto mode
  instead uses a background classifier that blocks force pushes, `git reset --hard`,
  `git clean -fd`, `git stash drop/clear`, amending commits that are not the session's own,
  printing live credentials, `curl | bash`, unapproved remotes and similar. It also respects
  boundaries stated in the conversation. On 2.1.283 and later it is the built-in default for
  terminal sessions, and it is available in the desktop app. This session reports
  `permissionMode: "bypassPermissions"`. The desktop settings show bypass "allowed (user opts
  in)" and auto mode "allowed". Meanwhile `AGENTS.md`, `CONTRIBUTING.md` and the environment
  notes contain hard rules: never force-push, never read source CLI credentials, no release,
  tag or dispatch actions, never bare `git stash`. Nothing on this host enforces them.
- **Evidence.** permission-modes page, mode table, "What the classifier blocks by default" and
  "Skip all checks with bypassPermissions" (2026-10-08). sandboxing page, platform statement
  (2026-10-08). `mcp__ccd_session_mgmt__get_session self`. `mcp__ccd_settings__get_settings`.
  `CONTRIBUTING.md` Git policy. `AGENTS.md` "Boundaries and completion".
- **Label.** Fact for the mode and the docs. Inference that the risk is real for this owner,
  given many parallel unattended sessions plus external provider payloads and web content.
- **Confidence.** High.
- **Impact.** Quality and safety: high. Prompt injection from provider payloads or web pages
  currently has no backstop. Speed: auto mode adds classifier latency and occasional false
  blocks. It still needs no routine owner clicks.
- **Proposed direction.** Make **auto** the default for this project's sessions (Desktop
  Settings, or `permissions.defaultMode: "auto"` in user settings) and keep bypass for
  deliberate disposable-VM work. Pair it with the hard deny rules in B1-F3. State standing
  boundaries once in `AGENTS.md` ("never push anywhere except `origin main`"); the classifier
  reads conversation boundaries but can lose them after compaction, so hard guarantees belong
  in deny rules.
- **Verdict.** **Trial** for one week of normal work, then adopt if false blocks stay rare.
  This is the owner's call because it changes host trust posture (open question 1).
- **Security/supply-chain.** Reduces risk. No new dependency.
- **Effort and upkeep.** One settings change. Watch for blocked routine commands, e.g.
  `git push origin main` should pass because it is in the trusted remote.
- **KEEP.** Keep the existing prose rules. They also guide the classifier.

### B1-F3 — Add a small committed project `.claude/settings.json` with hard deny rules
- **Observation.** The docs say deny rules block in every mode including bypass, and are
  evaluated before ask and allow. PowerShell rules use the same shape as Bash rules, with alias
  canonicalisation. Read/Edit deny rules also cover recognised shell readers (`cat`, `head`,
  redirects), but not arbitrary subprocesses. On Windows, approvals granted inside a worktree
  stay with that worktree; they are not saved to the main checkout. The repo has no project
  `.claude/settings.json`. Only a gitignored `settings.local.json` exists, allowing
  `Skill(update-config)`. User settings allow only one Edit path.
- **Evidence.** permissions page, precedence, PowerShell rules and Read/Edit rule limits
  (2026-10-08). worktrees page, "What worktrees share with the main checkout" (2026-10-08).
  `git ls-files .claude` (none tracked). `C:\Users\danii\.config\git\ignore` (ignores
  `settings.local.json`).
- **Label.** Fact plus external-claim.
- **Confidence.** High that the mechanism works. Medium on the exact pattern set, because
  argument patterns are documented as fragile.
- **Impact.** Quality and safety: medium-high. Speed: neutral.
- **Proposed direction.** One committed file, about 10 rules, so every worktree gets it:
  - Deny `Bash(git push --force*)`, `Bash(git push -f*)`, `Bash(git push * --force*)`,
    `Bash(git push * -f*)`, plus `PowerShell(...)` twins.
  - Deny `Bash(git stash pop*)` and `Bash(git stash drop*)`.
  - Deny `Bash(gh release *)` and `Bash(gh workflow run *)`, so Preview dispatch and releases
    stay owner actions.
  - Deny `Read`/`Edit` on the source-CLI credential stores the app reads. Get exact paths from
    `docs/providers`. Examples: `Read(~/.claude/.credentials.json)` and `Read(~/.codex/auth.json)`.
  - Add allow rules later, only if auto-mode latency hurts. `/fewer-permission-prompts`
    generates a read-only allowlist from transcripts.
  - Bash patterns are bypassable through `sh -c` and similar, so treat these rules as a
    backstop, not a boundary.
- **Verdict.** **Adopt.** It answers a concrete current need: hard rules with no enforcement.
- **Security/supply-chain.** A committed settings file is project config that a PR could weaken.
  The repo is owner-only plus DCO PRs, so review settings diffs as security-relevant.
- **Effort and upkeep.** 30 minutes. Revisit when provider credential paths change.
- **KEEP.** Keep `settings.local.json` personal.

### B1-F7 — Worktree sprawl: 31 merged, clean worktrees are retained
- **Observation.**
  - Desktop sessions with the worktree option live under `<repo>/.claude/worktrees/`.
  - Archiving a session removes its worktree.
  - "Auto-archive after PR merge or close" fires only for PRs, and "Archive inactive sessions"
    can archive idle sessions after N days, keeping any worktree with uncommitted changes.
  - Subagent worktrees are swept after `cleanupPeriodDays` only if they hold no work.

  Host state:
  - 33 worktrees. 31 have HEAD already contained in local `main` and no uncommitted changes:
    18 desktop sessions and 13 `agent-*` subagent worktrees.
  - Auto-archive on PR close is on, but the owner merges straight into `main` without PRs, so
    it never fires.
  - Inactive-days archiving is 0 (never).
  - Branch prefix is `users`.
- **Evidence.** desktop page, "Work in parallel with sessions" (2026-10-08). worktrees page,
  "Clean up subagent and background-session worktrees" (2026-10-08). `git worktree list`
  merged and dirty classification run 2026-10-08. `get_settings`.
- **Label.** Fact.
- **Confidence.** High.
- **Impact.** Speed and hygiene: medium. Disk use, slower `git worktree` and branch listings,
  stale sessions in the sidebar, and confusion over which worktree holds work. Quality: low.
- **Proposed direction.**
  - Set "Archive inactive sessions" to 7 days. The archive is safe for dirty worktrees per the
    docs.
  - Add one closing step to the merge procedure: after "Pushed to `main`" is verified, archive
    the session. The desktop asks for confirmation once.
  - Make a one-time cleanup of the 31 merged worktrees. This needs owner approval; it is
    destructive to session history even if the code is merged.
  - Separately, resolve the `CONTRIBUTING.md` "no branches" wording versus the worktree
    practice, for A1/D-196.
- **Verdict.** **Adopt** the inactivity archive and the merge-time archive step.
- **Security/supply-chain.** None.
- **Effort and upkeep.** 10 minutes, after which cleanup runs automatically.
- **KEEP.** Keep worktrees inside the project, the `users` prefix and D-196 placeholder
  numbering.

### B1-F8 — Use built-in `/code-review` and `/security-review` as inputs to the required review, not replacements
- **Observation.**
  - Best practices recommend an adversarial fresh-context review before calling work done,
    telling the reviewer to flag only correctness or requirement gaps to avoid
    over-engineering.
  - The bundled `/code-review [low…max|ultra]` reviews the current diff for bugs in a fresh
    subagent. `--fix` applies findings.
  - `/security-review` reviews the branch against origin's default branch for injection, auth
    and data-exposure risks.
  - `/simplify` covers reuse and abstraction level, not bugs.

  The repo's `convergence-review` skill and `aiu-reviewer` agent check spec and acceptance
  compliance, but no step specifies a bug-hunting or security pass. CONTRIBUTING requires
  focused independent review for credential, destructive-data or privilege changes.
- **Evidence.** best-practices page, "Add an adversarial review step" (2026-10-08). commands
  page rows for `/code-review`, `/security-review` and `/simplify` (2026-10-08).
  `.agents/skills/convergence-review/SKILL.md`. `CONTRIBUTING.md` "Review and integration".
- **Label.** External-claim for the commands. Inference on fit.
- **Confidence.** Medium. I did not measure false-positive rates on this codebase.
- **Impact.** Quality: medium-high for auth and storage changes. Speed: about 2 to 10 minutes
  per review.
- **Proposed direction.**
  - Add one line to `convergence-review`: for changes under the security-lifecycle scope, also
    run `/security-review` on the worktree branch before merge.
  - For larger feature diffs, optionally run `/code-review high`.
  - Triage findings against acceptance criteria, and record dismissed ones briefly.
  - Do not use `ultra`, which is a paid cloud review with code upload, without owner approval.
- **Verdict.** **Trial** on the next two security-scoped changes.
- **Security/supply-chain.** Local review commands keep code on the existing Anthropic path.
  `ultra` and cloud reviews send the repo to cloud sandboxes, so the owner decides.
- **Effort and upkeep.** Prose-only change.
- **KEEP.** Keep `aiu-reviewer` for spec compliance and "zero findings is valid".

### B1-F9 — `/goal` gives a verifiable autonomous finish without new configuration; reject a heavy Stop-hook gate
- **Observation.**
  - `/goal <condition>` is a session-scoped, prompt-based Stop hook.
  - After each turn a small model judges, from the transcript only, whether the condition is
    met, and if not, Claude continues.
  - It works in the desktop app, combines with auto mode for unattended runs, and stops when
    progress stalls. Evaluator cost is described as negligible.
  - A settings-level Stop hook instead fires after every response, not just at task end. It
    must handle `stop_hook_active`, because Claude Code overrides a hook that blocks eight
    times in a row.

  Repo checks are `dotnet run` suites with Defender first-run delays, so a per-turn Stop gate
  running them would be slow and noisy.
- **Evidence.** goal page (2026-10-08). hooks-guide, "Limitations" and "Stop hook hits the block
  cap" (2026-10-08). README "Local checks". Memory host facts.
- **Label.** External-claim plus inference.
- **Confidence.** Medium.
- **Impact.** Speed: medium-high, with fewer "continue" nudges from the owner. Quality: medium,
  because it forces explicit evidence of the acceptance checks in the transcript.
- **Proposed direction.** For substantial tasks, the agent states its acceptance checks, which
  `AGENTS.md` already requires, and the owner or the agent sets
  `/goal <checks pass with output shown, git diff --check clean, verification record updated; stop after N turns>`.
  Add no Stop hook.
- **Verdict.** **Trial** `/goal`. **Reject** a settings Stop-hook verification gate for now.
- **Security/supply-chain.** None. It needs hooks enabled, which they are by default.
- **Effort and upkeep.** None, because it is per session.
- **KEEP.** Keep the PASS / FAIL / NOT_RUN / BLOCKED honesty rule. The evaluator only judges
  what is shown.

### B1-F10 — Hooks: little current need; Windows constraints raise their cost
- **Observation.**
  - Typical hook uses are formatting after edits, blocking protected files, notifications,
    re-injecting context after compaction, and audit.
  - The docs advise hooks for actions that must happen every time.
  - On Windows, shell-form command hooks run in Git Bash by default; `"shell": "powershell"`
    is available.
  - The doc examples rely on `jq`, which is not installed here. Only Windows PowerShell 5.1
    exists, with known native-redirect quirks.

  Repo state: no hooks. The desktop already notifies on input-needed and task completion.
  Formatting is optional (`dotnet format --verify-no-changes` on validator projects only).
  Hard blocks are covered by deny rules (B1-F3), and context re-injection is not needed because
  `AGENTS.md` loads natively.
- **Evidence.** hooks-guide (2026-10-08). hooks reference, `shell` field (2026-10-08).
  `command -v jq` returned nothing. Memory: no pwsh 7. `get_settings` notifications.
- **Label.** Fact plus inference.
- **Confidence.** Medium-high.
- **Impact.** Low today.
- **Proposed direction.** Add hooks only when a concrete need appears that a deny rule or
  `/goal` cannot express. The most plausible future candidate is a PreToolUse hook to check
  writes into `docs/providers` fixtures for credential-like strings. Use `shell: powershell`
  with `ConvertFrom-Json`, and avoid `jq`.
- **Verdict.** **Reject** for now under the simplicity rule.
- **Security/supply-chain.** Hooks run arbitrary commands with user privileges, and
  committed project hooks need workspace trust. Fewer is safer.
- **Effort and upkeep.** None.
- **KEEP.** Keep relying on desktop notifications.

### B1-F12 — C# code intelligence plugin (`csharp-lsp`) exists officially; defer the decision to B3
