## Findings

### B4-F1 — Auto memory is already shared by all worktree sessions; per-worktree project folders hold transcripts only
- **Observation:** There are 25 project folders for this repo under `~/.claude/projects/`, one for each worktree path. Only the main-checkout folder has a `memory\` directory: 8 files, 9.7 KB, the `MEMORY.md` index plus 7 topic files. The 24 worktree folders contain only session transcripts (`*.jsonl`). This worktree session still loaded the main `MEMORY.md` at startup.
- **Evidence:** The memory docs say "The `<project>` path is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory", with scope "Per repository, shared across worktrees". Auto memory is "machine-local". The folder comparison and this session's loaded context agree with the docs.
- **Label:** Verified (official docs plus local observation).
- **Confidence:** High.
- **Impact:** Quality neutral, speed neutral. The audit premise that worktree sessions might lack memory is false, so no fix is needed.
- **Proposed direction:** Change nothing. Do not add `CLAUDE.local.md` for personal rules. The docs say a gitignored `CLAUDE.local.md` "only exists in the worktree where you created it". A `CLAUDE.local.md` also counts as a CLAUDE file for the rule that decides whether `AGENTS.md` is read directly, which is harmless here only because `CLAUDE.md` imports `AGENTS.md`.
- **Verdict:** KEEP the current mechanism.
- **Security/supply-chain:** None. Memory stays local and is outside git.
- **Effort and upkeep:** None.
- **KEEP:** Yes.

### B4-F2 — Five of the seven memory topics repeat rules that already live in the repo
- **Observation:** These memory topics restate rules already in the repo:

  | Memory topic | Repo location of the same rule |
  |---|---|
  | UI design variants first | `AGENTS.md:18-21` |
  | Post-deploy owner checks | `AGENTS.md:87`, `docs/workflow/verification.md:60` (D-190) |
  | State push status | `AGENTS.md:93-96` |
  | Numbers at merge | `CONTRIBUTING.md:59-60`, D-196, `docs/workflow/formats.md:47` |
  | No repeated approval gates | `AGENTS.md:17`, `CONTRIBUTING.md:19,25` |

  All five were written 2026-10-07/08, the same days the repo text was written. Every session therefore loads each rule twice: the index line plus `AGENTS.md`.
- **Evidence:** The docs say auto memory "skips anything your CLAUDE.md files already say". They also warn that "if two instructions contradict each other, Claude may pick one arbitrarily", and that user rules and project rules do not override each other. The current copies agree in meaning, but a later edit to one copy without the other will silently create conflicting instructions.
- **Label:** Curation problem (duplication, future drift).
- **Confidence:** High for the duplication, Medium for the risk.
- **Impact:** Quality: drift risk on exactly the rules the owner corrects most. Speed: small context cost, under 1k tokens.
- **Proposed direction:** Make the repo the single source for any rule about how work on this repo is done. Remove those five topic files and their index lines, or reduce each to a one-line pointer such as "see AGENTS.md › UI variants". Use `/memory` or the available `consolidate-memory` skill, and only with the owner's yes, because the memory is the owner's own. Going forward: when the owner states a repo-wide rule in conversation, the agent writes it into `AGENTS.md`, `CONTRIBUTING.md` or a decision, not into memory.
- **Verdict:** Adopt (curation only, no new mechanism).
- **Security/supply-chain:** None.
- **Effort and upkeep:** About 10 minutes once. After that, the rule above prevents the duplication from coming back.
- **KEEP:** No (change).

### B4-F3 — Two memory topics hold facts that belong only in memory; one quietly narrows a repo decision
- **Observation:**
  - "Host tooling constraints" holds machine facts: no pwsh 7, Defender first-run latency, IPv6/0x80072EFE, worktree agent loading, locked-desktop limits. Only the IPv6 item appears in the repo (`README.md:144`). Machine-local facts are what auto memory is for.
  - "Claude Code only" records that Codex/Astra are disabled. That is an owner workflow policy that narrows the repo's agent-neutral decision (D-012) and its reviewer-family wording, but it exists only in private memory. Anyone reading only the repo, such as a future non-Claude tool or a fresh clone on another machine, cannot see it.
- **Evidence:** Memory topic names and sizes (about 1-2.4 KB each). `docs/decisions/accepted.md` D-012. `grep` of AGENTS.md, CONTRIBUTING.md and docs/workflow finds no pwsh/Defender/locked-desktop text.
- **Label:** Placement question.
- **Confidence:** Medium.
- **Impact:** Quality: review lanes may plan cross-family review that the owner has disabled. Speed: small.
- **Proposed direction:** Keep the host facts in memory. Facts that affect verification steps (Defender latency, locked desktop) could also get one line in `docs/workflow/environment.md` if the owner wants them to survive a machine change. Ask the owner whether "Claude Code only" is durable. If it is, record it as a `D-NEW` amendment to D-012 so the repo and memory agree. If it is temporary, keep it in memory only.
- **Verdict:** Adapt (owner decision).
- **Security/supply-chain:** None. Do not copy any host or account specifics beyond what is needed.
- **Effort and upkeep:** Minutes.
- **KEEP:** Partly.

### B4-F4 — Agents can find decisions fine; the problem is that amended decisions do not point to their amendments
- **Observation:** `accepted.md` has 205 `### D-NNN - Title` entries (10,769 words, about 14k tokens), with consistent headers that grep handles easily. `AGENTS.md` tells agents to search there. Finding a decision is not the issue; the content is:
  - **One-way amendment links.** 18 of the recent entries (D-180…D-206) say they amend, replace or supersede 21 earlier entries. None of the earlier entries carries an "amended by" note (`grep "amended by D-\|superseded by D-"` → 0). Example: D-193 still says settings "slides in from the right edge and narrows the cards". Only D-197 says it "amends D-193's sheet". D-203 replaces part of D-199, and D-199 does not say so. An agent that greps for D-193, or is pointed to it from a spec (specs cite D-184…D-187 30-60 times each), reads a stale rule.
  - **Stubs.** 20 entries (D-013…D-017 and similar) are only "superseded by CONTRIBUTING", and a superseded register with 43 entries already exists.
  - **Heavy churn.** 25 commits touched `accepted.md` on 2026-10-08 alone, and 38 since 2026-10-01. The large "Owner UI amendments" section keeps growing with fine UI detail; D-187 is 484 words.
- **Evidence:** The counts above. `docs/decisions/accepted.md:593-672`. The "Superseded register" convention described at the top of `accepted.md`.
- **Label:** Curation problem (not retrieval).
- **Confidence:** High.
- **Impact:** Quality: high, because stale UI rules can be re-implemented or "restored" as fixes. Speed: medium, because agents must read neighbouring entries to be safe.
- **Proposed direction:**
  1. When a new decision amends `D-x`, the same commit adds one line under `D-x`: "Amended by D-y (date): gist."
  2. The existing `AiUsage.ProjectValidation` check could flag an "amends/replaces D-x" that has no matching "Amended by" note. This is a small extension of an existing validator, not a new tool. Check with lane A-x for validator scope.
  3. Move the 20 stubs to `superseded.md`, leaving the ID to point there.

  Do not restructure into one file per decision now.
- **Verdict:** Adopt (convention plus a small validator rule).
- **Security/supply-chain:** None.
- **Effort and upkeep:** About 1-2 h once to back-fill 21 markers and move stubs. Each later amendment costs one line.
- **KEEP:** No (change).

### B4-F5 — Fine-grained UI decisions blur the line between decision and spec
- **Observation:** D-180…D-206 record exact copy, tooltips, key bindings and pixel-level behaviour, for example D-193 and D-197 (198-484 words each). The same detail is then copied into the AIU spec folders. Two places describe the same UI, which is where the stale-rule risk in F4 comes from.
- **Evidence:** Word counts per entry; the spec citation counts in F4.
- **Label:** Curation (design question).
- **Confidence:** Medium. This is a judgement and the owner may want this granularity.
- **Impact:** Quality: medium. Speed: small to medium (decision entries take longer to write and review).
- **Proposed direction:** Option for the owner: a decision states the rule and the choice ("variant B: settings drops down over the body; window opens at minimum width"), and the spec holds the copy and interaction detail and links to the decision. Smaller decisions mean fewer later amendments.
- **Verdict:** Adapt idea (owner choice; not urgent).
- **Security/supply-chain:** None.
- **Effort and upkeep:** Applies to new decisions only. Zero migration.
- **KEEP:** Owner decides.

### B4-F6 — `docs/` is large but well organized for grep; no index or knowledge graph is needed
- **Observation:** `docs/` has 237 files and about 326k words. Specs make up 262k words (80%) in 38 `AIU-NNN-slug/` folders, each with spec, tasks and verification files. Workflow docs are 20.8k words, decisions 16.6k, providers 8.3k, archive 1.6k. The always-loaded text is `AGENTS.md` (817 words, about 100 lines, under the documented "under 200 lines" target). `MEMORY.md` is 1 KB (limit 200 lines / 25 KB). Retrieval works by naming convention (the AIU-ID folder) plus `backlog.md` (11k words) plus grep.
- **Evidence:** The measurements above. The AGENTS.md "Read by task" table routes each kind of question.
- **Label:** Verified sizing.
- **Confidence:** High.
- **Impact:** At this size, Glob/Grep over Markdown takes seconds. A semantic index would save little and adds a stale index.
- **Proposed direction:** Keep the layout. The only retrieval cost worth cutting is `backlog.md` at 11k words, if agents read it whole; that is a lane for whoever owns backlog format. Path-scoped `.claude/rules/` (for example moving the "Useful logging" section) are Claude-only and would split the agent-neutral single entry point (D-012); not worth it while `AGENTS.md` is under 200 lines.
- **Verdict:** KEEP. Reject `.claude/rules` for now.
- **Security/supply-chain:** None.
- **Effort and upkeep:** None.
- **KEEP:** Yes.

### B4-F7 — Shared skills in `.agents/skills` are not discovered by Claude Code, so "use the X skill" depends on the agent opening the file itself
- **Observation:** `AGENTS.md` says "use the provider-evidence skill", security-lifecycle and convergence-review. Those live only in `.agents/skills/*/SKILL.md`. Claude Code's skill discovery covers `~/.claude/skills`, `.claude/skills`, nested `.claude/skills`, `--add-dir` and plugins. The skills docs do not mention `.agents/skills`. This session's skill list does not contain the three repo skills.
- **Evidence:** The skills docs location table, accessed 2026-10-08. `ls .claude` shows only `agents/` and `settings.local.json`.
- **Label:** Retrieval gap (a real one, small).
- **Confidence:** High for the facts. Medium for the impact, since agents often do open the file.
- **Impact:** Quality: medium, because security-lifecycle guidance can be skipped without the agent noticing. Speed: small.
- **Proposed direction:** Simplest fix: write the explicit path in `AGENTS.md` ("read `.agents/skills/provider-evidence/SKILL.md`"). Alternative: a `.claude/skills/<name>` symlinked folder. The docs say symlinked skill folders are supported, but Windows symlinks need Developer Mode or admin rights, and I have not checked junction behaviour. Hand this to lane A3 (agent tooling), which owns it.
- **Verdict:** Adapt (cross-lane).
- **Security/supply-chain:** None.
- **Effort and upkeep:** Minutes.
- **KEEP:** No (change).

### B4-F8 — Graph and vector memory servers (Graphiti, mem0/OpenMemory, MCP memory server, Basic Memory): reject
- **Observation:** All four add a second memory store next to the repo and native auto memory. None of them fixes F4, which is a curation problem.
  - **Graphiti:** active (v0.30.2, 2026-09-08; Apache-2.0). Its MCP server is described as experimental and needs Python 3.10+, FalkorDB or Neo4j (Docker Compose) and an LLM API key for extraction.
  - **mem0:** the documented Claude Code path is the hosted Platform MCP with an API key. That sends conversation-derived facts off-machine, against local-first D-006 and the repo's opaque-provider-data rule. OpenMemory (local) needs extra services.
  - **MCP reference memory server:** stores an entity/relation graph in a JSONL file outside git, so it cannot be reviewed or diffed.
  - **Basic Memory:** v0.23.2, 2026-08-25, AGPL-3.0. It keeps Markdown files, which is what the repo already does.
- **Evidence:** The sources listed in Scope. GitHub metadata pulled 2026-10-08.
- **Label:** Skeptical evaluation.
- **Confidence:** High.
- **Impact:** For one owner with about 39k lines of C#/XAML and about 326k words of docs, a graph's relational queries ("which decision affects this card?") come down to a grep for `D-NNN` or the AIU folder. Costs: setup, a DB process, LLM spend, index drift, and a new place for stale facts.
- **Proposed direction:** None.
- **Verdict:** Reject.
- **Security/supply-chain:**
  - Memory written by agents from provider payloads becomes a persistent prompt-injection channel that outlives the session.
  - `uvx`/`npx` launch-time installs are an unpinned supply-chain risk.
  - Hosted mem0 means data egress.
- **Effort and upkeep:** Hours to set up, then ongoing curation of a second store.
- **KEEP:** n/a.

### B4-F9 — Code-graph MCPs (codebase-memory-mcp, GitNexus, Serena, code-graph-rag): reject for this repo size
- **Observation:** The code base is 268 `.cs` files, about 39k lines with XAML, in three projects. Candidates:
  - **codebase-memory-mcp:** MIT, v0.11.0 2026-09-15, Windows amd64 binary. Its README says it "writes to your agent configuration files" and serves a localhost:9749 UI.
  - **GitNexus:** PolyForm Noncommercial. `analyze` "registers Claude Code hooks, and creates `AGENTS.md` / `CLAUDE.md` context files" and mirrors skills into `.agents/skills/`. That directly rewrites this repo's governed instruction files.
  - **Serena:** GPL-3.0 application, v1.7.0 2026-08-09, lists C#, installed via uv. It has its own `.serena/memories/`, which would be a third memory store.
  - **code-graph-rag:** MIT, v0.1.38, pre-1.0.
  - **Aider repo map:** Aider's last release was v0.86.0 in 2025-08 and its last push 2026-05, so it is slowing down; it is not usable inside Claude Code anyway.
- **Evidence:** GitHub API and README text, accessed 2026-10-08.
- **Label:** Skeptical evaluation.
- **Confidence:** High for maturity and licensing. Medium for the benefit estimate (no benchmark on this repo).
- **Impact:** Small. Symbol navigation in 268 files works with Grep/Glob, and these tools mainly pay off on much larger codebases. Some of them mutate agent configuration, which conflicts with the owner-controlled `AGENTS.md`.
- **Proposed direction:** None now. If symbol navigation becomes a measured bottleneck, look first at a first-party C# LSP plugin in Claude Code's official marketplace (lane A3; I did not verify one exists) rather than a third-party graph.
- **Verdict:** Reject (GitNexus clearly; the others until there is a measured need).
- **Security/supply-chain:**
  - Third-party binaries or installers run with repo read access and write to agent config.
  - Hooks run on every tool call.
  - The local web UI port opens a small attack surface.
- **Effort and upkeep:** Install, plus re-indexing on every worktree.
- **KEEP:** n/a.

### B4-F10 — Native curation tools cover most of the upkeep for free
- **Observation:**
  - Claude Code has `/doctor prompt-audit`, which checks CLAUDE.md, AGENTS.md, rules, skills and subagents for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other".
  - `MEMORY.md` length warnings are built in.
  - The `consolidate-memory` skill is available in this environment.
  - Past conversations can be searched with the desktop session-transcript search tool. Transcripts are deleted after `cleanupPeriodDays`, so durable "why" answers must still end up in decisions.
- **Evidence:** The memory docs (prompt-audit and limits sections) and the skill list in this session.
- **Label:** Verified availability; usefulness not measured here.
- **Confidence:** Medium.
- **Impact:** Quality: catches drift between `AGENTS.md`, agents and memory (F2/F3). Speed: neutral.
- **Proposed direction:** The owner runs `/doctor prompt-audit` after workflow-rule changes, or monthly, and approves fixes. Note that prompt-audit does not cover `docs/decisions`; F4's validator rule covers that.
- **Verdict:** Trial.
- **Security/supply-chain:** First-party. The report is read-only until fixes are approved.
- **Effort and upkeep:** A few minutes per run.
- **KEEP:** n/a.

### B4-F11 — The minimal knowledge setup for this repo
- **Observation:** Every layer already exists. What is missing is a stated rule for which layer owns what, plus F4's back-links.
- **Proposed direction:**

  | Layer | Owns | Curated by | Worktree reach |
  |---|---|---|---|
  | `CLAUDE.md` → `AGENTS.md` | Always-on rules, under 200 lines, routing table | Agent edits, owner approves | Git (every worktree) |
  | `CONTRIBUTING.md`, `docs/workflow/*` | Procedures, Git/review/verification policy | Same | Git |
  | `docs/decisions/accepted.md` | Durable owner rules, one entry each, two-way amendment links | Agent writes at the decision, validator checks links | Git |
  | `docs/specs/AIU-*` | Feature detail, UI copy, evidence | Task agent | Git |
  | `.agents/skills/*` | Multi-step procedures, referenced by explicit path | Agent/owner | Git |
  | Auto memory (main project folder) | Only machine/host facts, the owner's personal preferences not tied to this repo, and pointers. Never copies of repo rules | Claude, plus the owner via `/memory` | Shared by every worktree on this machine (F1) |

  Write-time rule: when the owner gives a direction in conversation, the agent asks "repo-wide rule?". If yes, it goes to AGENTS/CONTRIBUTING/decision. Memory is only for things that are not about how this repo is run.
- **Verdict:** Adopt (documentation of an existing practice: about 3 lines in AGENTS.md or CONTRIBUTING.md, no new tooling).
- **Security/supply-chain:** None.
- **Effort and upkeep:** Under 1 h total including F2/F4.
- **KEEP:** Structure yes, rules added.
