5 · Motion

Three durations, one easing family. m1 150 ms hover/focus/selection (ease‑out). m2 200 ms expand, tab and page entrance (cubic-bezier(.1,.9,.2,1), Fluent decelerate, 6 px rise + fade). m3 320 ms quota meter width and value colour after an actual new reading (cubic-bezier(.2,0,0,1)). Indeterminate work uses a 1 s linear rotation of the refresh glyph or a 12 px ring; determinate work (download, export, restore) uses a linear‑filled 4 px bar driven by real progress. Success acknowledgement is a 1.5 s fade‑in/out “✓ Updated” label; there is no motion for failures beyond the alert appearing. Nothing loops decoratively; nothing delays a command. Reduced motion (Windows setting or demo toggle) sets every duration to 0 and replaces spinners with static text — all states remain readable because every animation is paired with text.

6 · Loading versus refreshing

No data yet

Skeleton mirrors the final layout (four stat blocks, four rows with label, meter and numeral placeholders) so nothing shifts on arrival. Shimmer is a 1.6 s ease‑in‑out sweep between skel and skel2 (warm greys in Light, low‑delta greys in Dark). A skeleton is bounded by its result: failure renders the error row with retry, no accounts renders the empty state; it never persists. History uses the same rule for its chart area.

Refreshing existing data

Values stay visible. The refresh glyph on the affected row rotates and a compact “Updating…” with Cancel appears to its right in a fixed‑height slot, so the row never changes height; the freshness pill is untouched, so “Updating…” never implies healthy or fresh data. The last successful timestamp is retained until a reading arrives; then meter width and colour interpolate over m3 and “✓ Updated” fades for 1.5 s. On failure the values, freshness and timestamp remain, an inline alert names the failure category and offers Retry or a countdown (retryAt).

7 · Themes

Settings › Appearance offers System (default), Light and Dark as a radio group with miniature previews. System follows UISettings.ColorValues / Application.RequestedTheme and updates immediately when Windows changes; Light and Dark ignore Windows changes. The preference is persisted through the preference adapter (memory‑only in demo). The transition is a 200 ms colour cross‑fade on surfaces and text; no flash, no loading state. The demo shell’s “Windows mode” control simulates the OS change so both behaviours can be checked. All screens, dialogs, tray flyout, chart, skeletons and component states read the same tokens, so theme coverage is complete by construction.
